# Workflow core — task lifecycle, stage graphs, acceptance, packets, schedules

Code map, pass 15 (2026-07-28). Files are canonical; SQLite is a projection. Every task mutation follows the same spine: `updateTaskFile` (file lock → parse → mutate → atomic write, `app/server/files/task-writer.server.ts:117`) → `reprojectTask`/`rebuildPath` → `recordAudit` → notifications/SSE. Layout: `projects/<slug>/project.md` and `projects/<slug>/tasks/<KEY>/task.md` (`app/server/files/file-store-root.server.ts:10,61,69`).

## task.md format

Parser/serializer: `app/server/files/task-file.server.ts` (format doc in its header, :22-54). Sections: YAML frontmatter → `## Goal` (prose) → `## Packet` (one fenced yaml block, absent when no packet) → `## Timeline` (newest-first `### <ISO> · <type> · <actor-ref>` events with optional `title:`/`to: agent` metadata lines and an `evidence:` row list). Structural lines inside event text are backslash-escaped bijectively (:56-77) so comments can't forge sections. Unknown sections and unknown frontmatter keys round-trip verbatim; malformed entries produce `FileDiagnostic`s, never a crash (:100-245). Duplicate known sections: first wins, duplicate preserved as an extra section (:334-343). Timeline event types (10): `comment completion github policy note quality transition blocked agent assign` (`app/schemas/task-file.schema.ts:47-58`); `policy` is reserved for genuine governance violations (P13-LV-03).

Frontmatter (strict target `taskFrontmatterSchema`, `task-file.schema.ts:441-483`; tolerant parse with per-field fallbacks :698-730): `key title stage readiness waiting ownerUserId engagements[] operator recommendations[] schedules[] urgent archived validation workRevision verdicts[] branch pr github createdAt updatedAt boardRank`. Enums: readiness = `ready|input_required|inconsistency_risk_detected|blocked` (:25); waiting = `human|agent|none` (:33); validation = `healthy|changed|failing|none` (:36) — a DERIVED cache only (see below). `pr.state` = `review|merged|closed|accepted` (:239) plus optional `checks`/`review`/`mergeable` caches (:281-318). Legacy `specialist`/`reviewers`/`consultants` keys are absorbed into `engagements` on read and not preserved (:743-783); duplicate profileIds are deduped first-wins (:789-799). Deleted `repo` override is now an unknown key, preserved verbatim (:471-475).

## Projects and project.md

`projectFrontmatterSchema` (`app/schemas/project-file.schema.ts:168-192`): `name slug archived repo defaultBranch taskPrefix nextTaskNumber stages[] workflow[] members[] agents[] credentialPolicy guardrails[]`; body = description. Stage = `{id,name,color}` (:40); workflow rule = `{from,to,boundary:auto|approval|human,by,locked}` (:50). `agents[]` are per-project deployments of org profiles with capability grants + optional loose `definition` override (:128-142). Task keys come from `allocateTaskKey` under a file lock, repairing stale reads and re-scanning max on-disk key so the counter never rewinds (`app/server/files/project-writer.server.ts:166-185`). Archived projects are read-only via the single `requireProjectMutable` chokepoint inside `requireAction` (`app/server/tasks/task-actions.server.ts:297-312`).

## Stage graph

- Template: the only preset is Governed-5 (`triage ready impl review done`) with boundaries auto/auto/approval/human(locked); the Lightweight preset was deleted by owner ruling (`app/shared/workflow/templates.ts:33-73`, rationale :16-23). `DEFAULT_GUARDRAILS` ship on every project (:81-87).
- The workflow is maintained as a CHAIN over stage order — one rule per consecutive pair. Stage add/remove/reorder auto-wire it: `spliceStageIntoChain` (`app/shared/workflow/transitions.ts:118`), `rejoinChainAroundStage` (merges with the STRICTER boundary, :183), `realignChainToStages` (:249). Any rule into the terminal stage is forced `human`+`locked` (:86-101); `stageFlowPath` walks real edges for the Policy map and reports unreachable stages as `offChain` (:284).
- Structural roles are derived, never hard-coded: entry = first, terminal = last, review = first stage with an edge into terminal (positional fallback), work = edge-into-review (`app/shared/workflow/stage-roles.ts:41-68`). Entry/terminal are rename-lockable only (`stageLockReason` :31).
- Per-board stage eligibility for agent profiles (R14-1): declared ids match literally, then by role alias (`todo→entry`, `doing/wip→work`, `qa→review`, etc., `app/shared/workflow/stage-eligibility.ts:34-55`); a declaration that resolves to NOTHING on this board means unrestricted (rule 3, :136-147). Enforced at assign/run time by `assertStageEligible` (`app/server/tasks/specialist-run.server.ts:1687-1704`).

## Transitions (`transitionStage`, task-actions.server.ts:2776)

Inputs: `manual` (admin|maintainer board move to ANY stage) and `rework` (operator-only, backward move on a `validation: failing` task, vetted at :2823-2830). Order of checks: idempotent same-stage → target exists → boundary lookup → off-graph refusal unless manual/rework (:2831). A HUMAN moving into the terminal stage is rerouted through the full `acceptCompletion` contract (:2845-2857); the operator is refused a bare move to Done (:2864-2867). RBAC per boundary: manual → `approve-transition`; auto crossed by a human → any member; approval → `approve-transition`; human → `requireAcceptCompletion` (maintainer+ or task owner, :2869-2889). The write: sets stage, clears `waiting` on Done entry, attaches the operator when leaving entry, resets a triage-default `input_required` to `ready`, recomputes derived validation on review entry, drops stale `transition` recommendations (:2903-2942). Side effects: every non-Done move re-invokes the operator with a threaded `transitionDepth`; `OPERATOR_TRANSITION_CHAIN_CAP = 8` consecutive operator-authored transitions opens a stuck-loop packet instead of another run (:118, :2983-3020). Entering the review stage fire-and-forgets `openReviewPrBestEffort` (:3028-3031). Drag-reorder (`reorderTask`, :3392) requires `reorder-board` and routes cross-stage drops through `manual: true` transition, then sets `boardRank` midpoints.

Operator-side (`operatorTransitionStage`, `app/server/tasks/operator-actions.server.ts:1532`): capability `stage-transitions` gates it; `auto` boundaries are performed directly even under `recommend` mode (they declare "no approval needed", :1542-1556); governed boundaries under recommend post a `transition` recommendation card; rework moves are direct. `gate()` promotes recommend→direct under full autonomy EXCEPT `completion-for-acceptance`, which must be explicitly `direct` (:227-241).

## Validation, revisions, verdicts (F10-15)

- A delivering run's reconciliation mints a `workRevision` `{id, headSha, treeSha, branch, sourceProfileId}` only when the head's TREE actually changed (`nextWorkRevision`, `task-file.schema.ts:629-657`; minting site `app/server/github/workspace-delivery.server.ts:341-384`; a zero-commit run mints nothing, P11-72).
- Verdicts bind to a revision id; a new revision makes old verdicts stale automatically (:503-510). Required reviewers = supporting engagements with the engage-time `verdictCapable` snapshot (:498-500).
- `deriveValidation` is the SINGLE intended writer of `validation`: `none` (no revision) / `failing` (any required reviewer requests changes on current revision) / `healthy` (all approved) / `changed` (pending) (:516-534).
- Verdict recording (`recordAgentCompletion`, task-actions.server.ts:1695-1825): envelope verdict first, else prose classifier `classifyReviewerVerdict` (:1595-1651) — only for verdict-AUTHORIZED agents, resolved from the engagement snapshot with live-grant fallback (:2085-2102); reply + verdict (`quality` event) + ask-human question land in ONE atomic write; a verdict-granted agent with no determinable verdict leaves validation unchanged and logs loudly (:2130-2145). Non-healthy verdicts drop pending `accept_completion` recommendations (:1794-1799).

## Acceptance gating

One shared gate, `acceptanceRefusalReason` (:4113-4135): archived → stage/graph position (`acceptanceStageBlockedReason` :4083 — only from the review stage or any stage with a declared edge into terminal) → required-reviewer approvals (`acceptanceBlockedReason`, schema :540) → open blocked packet → closed-unmerged PR (schema :576) → conflicting PR (schema :597). Four writers to Done consume it:

1. `acceptCompletion` (:4244) — human path; RBAC = maintainer+ OR task owner with contributor+ (`requireAcceptCompletion` :329, `ownerException` :315). Attempts the REAL PR merge first; GitHub-refused merge (conflict/moved head) refuses acceptance; unreachable merge records `pr.state: accepted` (merge pending) with the true cause (:4287-4306). Writes stage=terminal, readiness=ready, waiting=none, derived validation, clears packet + transition/accept recommendations, `completion` event (:4308-4345).
2. `resolvePacket`'s `accept_completion` option (:3683-3771) — same gates, plus F10-09 packet-identity re-check immediately before the merge side effect (`beforeMerge`, :3724-3741) and again inside the write lock (:3904-3916).
3. `operatorAcceptCompletion` (operator-actions.server.ts:1643) — supervised (or capability ≠ direct) posts an `accept_completion` recommendation card; FULL autonomy + explicit `completion-for-acceptance: direct` moves to Done itself but can never merge (PR stamped `accepted`, a human merges later, :1754-1800). All gates checked before BOTH branches so a card acceptance would refuse is never posted.
4. `forceAcceptCompletion` (:4365) — admin-only `force-accept-completion`; audits the exact bypassed gate, then accepts with `force: true` (skips refusal gates and the unmergeable refusal).

UI affordance comes from the one predicate `resolveAcceptanceAffordance` (:4194; hasAuthority × atBoundary × blockedReason), DB-free. `completeTaskMerge` (:4422) finishes a merge-pending acceptance later. Server push of the deliverer's workspace is gated by the delivering profile's `execute-code-or-write-repo` grant, conservative on unresolvable profiles (`resolveDeliveryPushGrant` :3045).

## Archive (R14-3)

`setTaskArchived` (:3498): RBAC `approve-transition`. Archiving sets `archived: true`, waiting=none, clears recommendations AND the packet, cancels pending/claimed schedules (P14-RV-03, :3563-3567), writes a `note` event naming everything withdrawn, and is reversible (restore sets waiting=human). Archived tasks leave the board default view/review queue and block acceptance (schema :616). The `archive_task` packet option re-checks `approve-transition` inside its case (:3858-3866), resolves the packet, then runs the real archive; `deleteBranch: true` additionally deletes the remote branch best-effort with every non-success outcome written to the timeline (:3971-4015); resolution of a deleteBranch option is refused while the PR is open (schema comment :364-367).

## Packets

One packet slot per task (`## Packet`). Shape: `{id, type: input|blocked, kind, from, title, body, observations[], options[], awaiting?}` (schema :372-393); option kinds (stable dispatch vocabulary, :62-83): `accept_completion request_edit block_on_policy hold_runtime_debug redirect retry_other_backend edit_goal archive_task custom`. Opened by the operator toolkit (`operatorOpenPacket`, operator-actions.server.ts:500 — capability `generate-packets`; blocked packets set readiness=blocked but NOT validation, F7-VAL1 :566-575) or by an agent's ask-human envelope (`buildAgentQuestionPacket` via recordAgentCompletion :1829-1841, never clobbering an open packet). The operator can withdraw a moot packet (`operatorResolvePacket` :628).

Human resolution (`resolvePacket` :3620): owner (contributor+, current member) OR `resolve-packet` (maintainer+) (:3660-3672); `accept_completion` defers to acceptance authority; `archive_task` re-checks approve-transition. Semantics per kind: `block_on_policy`/`hold_runtime_debug` keep the packet OPEN (no `clearPacket`) and set readiness=blocked; `edit_goal` stamps `awaiting: goal_edit` and `updateTaskGoal` (:524-596) clears it when the edit lands; `retry_other_backend` clears + starts the promised run under operator authority, recording failures on the timeline (:4022-4059); `request_edit|redirect|custom` set waiting=agent and re-invoke the operator (:3956-3962). Free-text notes are appended to the decision event as a blockquote (:3927-3931). Stale-resolution safety: `packetIdentity` (:3604) captured before awaits, re-checked in-lock.

Recommendations (the packet's many-at-once sibling): kinds `assign_specialist assign_reviewer transition run_specialist run_reviewer accept_completion` (schema :149-166); applied via `applyRecommendation` (:4489, `requireDecisionAuthority` = owner or resolve-packet :353) which executes the underlying governed mutation (inner RBAC still applies), or dismissed (:4624).

## Schedules

`scheduleTaskAction` (`app/server/tasks/schedule.server.ts:100`): only action is `run-operator`; future-dated, refused on terminal tasks; RBAC (run-agents) is trusted to the caller. Lifecycle `pending → claimed → fired | failed | cancelled` (schema :198-204). Runner: `startScheduleRunner` (boot at `app/server/boot.server.ts:233`) fires once at boot then every 60s, non-overlapping (:435-454). `fireDueSchedules` (:217) finds due rows via LIKE on the `schedules_json` projection column, claims the occurrence IN THE FILE first (crash-safe; stale claims past the 5-min lease are re-driven, :206,240-244), retires archived/Done tasks as `fired` with a skip note, then detached-runs `runOperator` with the schedule's backend+autonomy and `trigger: "manual"` (:361-367), finalizing to `fired` or bounded-retry back to `pending` (cap 3 → terminal `failed`, :379-408).

## Engagements (assignments)

One uniform `engagements[]` list; at most one entry `delivers: true` (workspace/branch/PR owner, single-writer invariant; schema :107-136). `assignSpecialist` (specialist-run.server.ts:273) replaces the deliverer (stage-eligibility asserted; refuses swapping while the outgoing deliverer's run is live, P14-GV-10 :307-322; audits handoff distinctly). `assignReviewer` (:410) appends a supporting engagement, idempotent across BOTH positions, snapshotting `verdictCapable` from the live grant at engage time. `removeReviewer` (:520) drops supporting entries only. The operator engages through `operatorEngageAgent` (delivers→assign-primary-specialist gate; supporting→summon-reviewers gate, operator-actions.server.ts:1382) and runs through `operatorRunAgent` (:1437 — a delivering run always runs the CURRENT deliverer; a mismatched profileId is refused, P11-22). Runs start via `startAgentRun` (:578) resolving the engagement by profileId (first match — the reason duplicates are corrupt).

## Operator triggering

`autoInvokeOperator` (task-actions.server.ts:603) — fire-and-forget, no-op without a deployed operator — fires on: task create (:514), goal update (:593), every non-Done stage move (:3002), packet send-back (:3961), and out-of-band PR divergence from the reconciler (`app/server/github/github-reconciler.server.ts:459-462`). Transition triggers carry from/to/byHuman context (:608-636). `runOperator` holds a process-level per-task lease with a newest-wins queued-trigger slot; token-guarded release fires the queued run and settles `waiting` (`app/server/runtimes/operator-run.server.ts:146-266`). Agent completions re-invoke the operator through the react loop (`operatorShouldReactToReply` :127 — new, non-duplicate reply, `OPERATOR_REACT_DEPTH_CAP = 4` :105); cap/no-progress opens a stuck-loop packet and always settles waiting off `agent` (:2380-2392). Operator authority resolves from the project's operator deployment (`resolveOperatorAuthority`, operator-actions.server.ts:155; autonomy default supervised, backend/model per deployment with override fallback).

## Suspect areas

- **`block_on_policy` still writes `validation = "failing"` directly** (task-actions.server.ts:3785) with an FR24 comment — contradicting the F10-15 "validation has ONE writer (deriveValidation)" rule stated at :4325-4332 and the F7-VAL1 decoupling documented in `operatorOpenPacket` (operator-actions.server.ts:566-575). A policy hold on a task with no review then reads "failing", and the next `deriveValidation` recompute (e.g. review entry) silently reverts it.
- **`block_on_policy` and `hold_runtime_debug` never clear the packet** (`clearPacket` stays false, :3772-3803) yet `markTaskPacketApprovalRead` runs (:3949), so the decision notification is consumed while the packet stays open and re-resolvable forever. Nothing else lifts `readiness: blocked` for these paths except a later goal-edit or operator withdraw — a hold decision has no documented "un-hold" affordance.
- **Direct `acceptCompletion` has no in-lock refusal re-check**: gates are evaluated on the pre-merge read (:4273-4285), then `attemptAcceptanceMerge` awaits network, then the write lock re-reads but re-checks nothing (:4321). A verdict/revision/packet change during the merge await is accepted anyway. The packet path got exactly this fix (P14-GV-05 `beforeMerge` :3724); the direct path did not.
- **Scheduled runs lose their note and identity**: `fireDueSchedules` invokes `runOperator` with `trigger: "manual"` (schedule.server.ts:366) — the operator prompt cannot distinguish a human poke from a scheduled re-check, and the human's `note` ("re-check X") only ever lands in the claim timeline note, never in the operator's directive.
- **Rework "backward" is positional, not graph-based**: both vetting sites compare stage array indices (task-actions.server.ts:2823-2830; operator-actions.server.ts:1598-1614). On a board whose column order doesn't match its chain (hand-edited workflow), "backward" diverges from the governed graph.
- **`fireDueSchedules` discovers due rows by `LIKE '%"status":"pending"%'` on JSON** (schedule.server.ts:224-228) — fragile against serialization changes and scans all matching rows every minute; correctness currently depends on the projection column staying verbatim JSON.
- **`schedule.server.ts` header comment is stale**: it still documents "flipped pending → fired BEFORE runOperator" (:32-34) while the code implements the F10-16 claim/lease flow — the comment describes the exact bug the flow replaced.
- **Two terminal-stage resolvers**: schedule.server.ts uses last-stage-positional via projections (:78-81) while task-actions uses `resolveStageRoles` on the file; they agree only while terminal = last. `operatorAcceptCompletion` also resolves Done positionally (operator-actions.server.ts:1656-1657).
- **`operatorAcceptCompletion` stacks four redundant gates** (:1667-1718): `acceptanceRefusalFor` already covers acceptanceBlockedReason, closedPr, and the blocked packet; the extra copies can drift (and the blocked-packet copy already differs in wording).
- **`reorderTask` can 403 halfway**: it requires `reorder-board` then delegates cross-stage drops to `manual: true` transition requiring `approve-transition` (:3411-3428) — a role granted the first but not the second gets an error after passing the visible gate; whether any real role tier splits these is worth confirming against `ACTION_ROLES`.

## Open questions

1. What should resolve a `block_on_policy` / `hold_runtime_debug` decision? Should choosing them close the packet and rely on the operator to reopen, or stay open as they do now — and if open, should their notifications stay unread?
2. Acceptance is legal from ANY stage with a declared edge into terminal (:4094-4097), but the review-stage role (PR opening, operator boundary) is the FIRST such edge only (stage-roles.ts:50-54). On a custom board with two edges into Done, is acceptance-from-both intended while only one stage opens PRs?
3. Should the full-autonomy operator ever be allowed to complete the real merge (today it always leaves `accepted, merge pending` for a human, operator-actions.server.ts:1754-1757), e.g. with a dedicated machine identity?
4. Scheduled re-runs: should `TaskSchedule.note` be threaded into the operator prompt as its directive, and should a distinct `schedule` trigger exist so the timeline/operator can attribute the run?
5. Is positional stage order authoritative for "backward" rework on hand-customized boards, or should rework follow reverse chain edges?
6. Stage-eligibility rule 3 (a declaration meaningless on this board → unrestricted, stage-eligibility.ts:22-25) trades silent-disable for silent-enable. Is unrestricted the right default for a profile explicitly scoped to stages that don't exist here?
7. `schedules` only supports `run-operator`. Are scheduled specialist runs / scheduled transitions (e.g. auto-archive stale tasks) wanted, or deliberately out of scope?
8. The owner exception admits a contributor-owner to accept their OWN task's completion (R6-2). Should an owner also be able to force-complete a merge-pending PR (`completeTaskMerge` allows it today via the same authority, :4437-4443) given merging writes to the shared repo?
