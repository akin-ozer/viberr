# UC-08 — Underspecified task → triage quality gate flags it; input_required + decision packet

## Purpose

Proves **FR15** (agents flag low-quality/underspecified tasks and request clarification
BEFORE execution), **FR26** (structured decision packets), **FR35** (task-quality issues as
first-class events), and **R16-2** (`input_required` joins the board's "Blocked or waiting"
attention chip). Mechanism under test:

- `triageQualityGate(snapshot)` (`app/server/runtimes/operator-run.server.ts:2136-2150`,
  F15-14): at the FIRST stage the turn instruction forbids a forward `transition_stage`
  until the goal names a deliverable + an acceptance signal; the options are `set_goal`
  (only when task text/repo make it unambiguous) or an `input` decision packet proposing
  2–4 concrete scopes.
- `operatorOpenPacket` (`app/server/tasks/operator-actions.server.ts:686-854`): one open
  packet at a time (B3), `task.operator.packet_opened` audit, `notifyTaskWatchers`
  "Decision needed" notification, waiting → human.
- `createTask` (`app/server/tasks/task-actions.server.ts:438-527`): a new task is born
  `readiness: input_required`, `waiting: human`, and an empty goal becomes
  `DEFAULT_GOAL` = `"Goal to be refined at the triage quality gate."` (:421); creation
  fire-and-forgets the operator with trigger `create` (:520).

**Standing live evidence**: VC-2 ("Improve the docs", goal "Make the documentation
better.") already sits at `triage / input_required` with exactly this operator packet
(`pkt_F5BjMy9l8t16`, opened 2026-08-05T23:15Z — 3 `custom` scope options + 1 `edit_goal`).
This runbook re-proves the gate on a fresh task so the full event chain is observed live.

## Steps

1. **Create a deliberately vague task.** [UI] Board → New task, or [API]
   `POST /projects/viberr-core/board` with `intent=create-task`,
   `title=Improve error handling`, `goal=The error messages could be better. Improve them.`
   (vague on purpose: no file, no change, no acceptance signal — the F15-14 canonical
   shape). Expect `{ok:true, key:"VC-<n>"}`; record `<KEY>`.
   - Immediate [API]: `task.md` exists with `stage: triage`, `readiness: input_required`,
     `waiting: human`, `engagements: []`, no `## Packet` yet.
2. **Observe the auto-invoked operator run** (trigger `create`). [API] poll `agent_runs`
   for `kind='operator'` on `<KEY>` → `queued`/`running` within ~5 s. [UI] task page →
   Agent logs shows the Operator streaming. Wait for `finished` (typically 1–3 min).
3. **Assert the gate held.** [API] read `task.md`:
   - `stage: triage` — NO forward transition happened.
   - A `## Packet` block: `type: input`, `from: operator`, `kind: Decision required`, a
     scoping title, `options:` of 2–4 entries whose kinds are from the valid set
     (expect `custom` scopes and/or `edit_goal`), exactly ONE `rec: true`.
   - `readiness: input_required`, `waiting: human`, `engagements: []` (FR15: clarification
     BEFORE execution — no specialist engaged, no specialist run rows in `agent_runs`).
   - Goal unchanged (the operator must not have invented a scope via `set_goal` for a goal
     this vague — that is the exact failure the gate text names).
4. **[UI] Board surface (R16-2):** the card sits in Triage with the input-required pill;
   the **"Blocked or waiting"** filter chip selects it.
5. **[UI] Task detail (FR25):** the Decision packet renders at the top, above the
   timeline, with its observations grid and options; one primary action per surface.
6. **[UI] Notification:** the bell / "Waiting on you" inbox has
   "Decision needed: <packet title>" for the task's watchers.
7. **[API] Audit:** Activity → Audit logs (or the audit_events table) shows
   `task.operator.packet_opened` with `{type: "input"}` and, from step 1, `task.created`.
8. **Single-packet invariant probe (optional, B3).** [API]
   `intent=run-operator` on `<KEY>` (manual trigger); wait for the run to end; re-read
   `task.md` → the packet `id` is UNCHANGED (a second turn must answer from the open
   packet, never replace it).
9. **Gate lifts on a concrete goal (optional continuation — starts real agent work).**
   [API] `intent=resolve-packet` `option=<index of the edit_goal option>` → packet stays
   with `awaiting: goal_edit`; then `intent=update-goal`
   `goal=Create qa/smoke/pass19-uc08-marker.md containing this task's key, a Purpose: line, and the date 2026-08-06, following qa/smoke/README.md conventions. Documentation-only.`
   → packet clears (updateTaskGoal fulfils it), operator re-fires with trigger
   `goal-updated` and now advances `triage → ready` (auto boundary). **Skip step 9 and go
   to Cleanup if you do not want the auto-chain to engage a specialist.**

## Failure signatures (findings)

- Operator advances `triage → ready` (or further) with the vague goal → **NEW HIGH**:
  F15-14 quality-gate regression (the New-task dialog's promise is broken).
- Operator `set_goal`s an invented scope (goal rewritten with no packet, no human input)
  → **NEW HIGH**: the "a scope you invented" failure the gate text forbids.
- Run finishes with NO packet, NO set_goal, task left `waiting: human` at an auto stage →
  stranded-operator class; check server log for the `maybeResumeStrandedOperator` chain
  and the "ended N consecutive runs" note (`operator-run.server.ts:525-563`); file NEW if
  the backstop did not engage.
- Packet observations describe the empty task workspace as "the repository" (e.g. "Repo
  contents visible to operator: only task.md") → **F19-4, already filed** (R19-1 rules a
  full read-only clone); record the repro, do not re-file.
- Step 8 replaces the open packet → **NEW HIGH**: B3 single-decision regression
  (`operator-actions.server.ts:731-738`).
- No "Decision needed" notification row → **NEW MED** (`notifyTaskWatchers` packet path).
- Board "Blocked or waiting" chip does not select an `input_required` card → **NEW MED**
  (R16-2 regression).
- The create turn itself errors (quota/auth) → not this UC's finding; the blocked
  "Operator run failed" packet is expected F-OP1 behavior. Re-run once; persistent
  environment failure = abort and note.
