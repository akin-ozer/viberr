# better-auth (sole auth system)

Viberr's authentication runs entirely on **better-auth 1.6.x**. better-auth owns
password + sessions + cookies + GitHub/Google OAuth + rate-limit, and its
`organization` plugin holds org/tenant membership. Project-scoped RBAC stays
file-native. The external-MCP OAuth surface is out of scope (the operator MCP is
in-process, no network surface).

There is **no legacy auth left**: no hand-rolled sessions, no dual-read fallback,
no backfill/migration pass, no OAuth callback plumbing. Those modules were
deleted; the legacy `sessions` table is dropped by migration `0014`.

## Architecture decision: bridge, not canonical-swap

better-auth's `user` table is NOT made the app's canonical user store. Rewiring
every profile/RBAC reader (org-users, user-admin, project_members projection,
user_prefs, audit) onto it would be a deep, risky refactor for no user-visible
gain. Instead:

- The legacy **`users` table stays canonical** for profile, org role, disabled,
  pwreset, theme, avatar, idp, github handle. Every existing reader is untouched.
- **better-auth owns** `user` (identity), `session`, `account` (credentials +
  OAuth links), `verification`, and the org tables (`organization`, `member`,
  `invitation`).
- **Invariant:** better-auth `user.id` === legacy `users.id`. `authenticate()`
  resolves a better-auth session, takes the user id, and loads the legacy
  `users` row for the `SessionUser`/`AuthContext` the app already consumes.
- **Single tenant:** one organization `org_viberr`; every user is a `member`
  whose `role` mirrors `users.role`. Viberr's hierarchical `roleSatisfies`
  check stays authoritative; the org plugin supplies the membership + invitation
  surface.

`app/server/auth/identity.server.ts` provisions the better-auth identity with
plain synchronous SQL at the moment a user is created (seed-admin, org invite,
demo seed, OAuth). There is no bulk backfill and no login-time reconciliation —
`provisionIdentity`/`setCredentialPassword`/`revokeUserSessions`/`deleteIdentity`
are called at the exact write points. The async better-auth API is used only for
the session read (`getSession`) and sign-in/out, in the route handlers.

## Passwords

No forced reset. better-auth's `emailAndPassword.password.{hash,verify}` hooks
are wired to Viberr's existing scrypt (`password.server.ts`), so the 6-part
`scrypt$N$r$p$salt$hash` strings verify verbatim. The backfill copies each
`users.password_hash` into a `credential` `account` row.

## Schema

`db/migrations/0013_better_auth.sql` is generated by
`scripts/gen-better-auth-schema.ts` from better-auth's own migration engine
(`getMigrations().compileMigrations()`), so the shipped DDL exactly matches what
better-auth queries. Regenerate on a better-auth version bump. Dates are stored
as ISO text, booleans as 0/1.

## Cookie / CSRF

Session cookie `viberr.session_token`, signed with `VIBERR_SESSION_SECRET`
(override with `BETTER_AUTH_SECRET`). `BETTER_AUTH_URL` is optional in dev
(origin inferred per request) and REQUIRED behind a reverse proxy.

`authenticate()` reads the better-auth session only (async) — `requireAuth`/
`requireUser`/`requireRole` are async and every call site awaits them. There is
no legacy fallback.

The hand-rolled double-submit CSRF is **kept** for the app's own mutating routes:
better-auth's Origin check only guards `/api/auth/*`, so board/task/etc. POST
actions still need it. The token derives from `AuthContext.sessionId` (now
better-auth's `session.id`), so it works unchanged with zero form edits.

## OAuth

better-auth social providers (GitHub/Google) + `account.accountLinking` link a
sign-in to the already-provisioned identity by verified email. `databaseHooks`
(`oauth-provision.server.ts`) gate NEW social users: allowed only when the email
is domain-allowlisted or a GitHub-handle placeholder exists (claimed by
replacement), else rejected. The hand-rolled OAuth callback/exchange modules and
`/auth/*` routes are deleted — better-auth serves `/api/auth/callback/*`.
GitHub-handle capture rides `user.githubHandle` (an additional field) into the
hook. Not live-verifiable here (no OAuth creds configured); covered by unit tests
(`oauth-provision.server.test.ts`).
