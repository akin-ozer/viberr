## 2. Same concern, different mechanism — and which wins

### 2.1 THE headline: two no-change completions (A-F19-21 vs B-R19-1/F19-21) — **unify, keep both halves**
| Axis | Session A | Session B |
|---|---|---|
| Mint moment | **Delivery time**: `performDelivery`'s non-`pushed` doors. `no_commits`, or `no_branch` when the task `neverDelivered` (no pr/revision/branch/cached commits) | **Verdict time**: `recordAgentCompletion`, agent reviewer approves a task with nothing delivered and no deliverer engaged |
| Evidence | **Workspace-side**: `push-workspace.server.ts` `DefaultBranchEvidence` — three read-only git probes (clean tree, no local commits ahead, no abandoned task branch); `verified:true` REQUIRED on both doors — a dirty tree / failed git read keeps the old refusal (the dirty-tree honesty gate) | **Remote-side**: `probeNothingToDeliver` live GitHub probe (ref 404 / compare aheadBy 0), fail-closed |
| Minted revision shape | `{headSha, treeSha: real, branch: defaultBranch, sourceProfileId: deliverer, NO kind}` via `resolveNoChangeBaseRevision` (returns null when GitHub unreadable — "an unverifiable base is not a verified no-change") | `{headSha: baseSha, treeSha: null, branch: null, sourceProfileId: null, kind: "verified"}` |
| Accept-time | **No live re-check.** Relies on: flag cleared when a PR opens (pre-existing), and required reviewers approving the minted revision through the ordinary ceremony | **Live re-probe in every writer to Done** (`acceptanceNoChangeCheck` + in-lock assert), force = audited disclosure, operator = no force |
| Event copy | Inline strings per writer (main's shape kept) | ONE shared `noChangeCompletionEvent` builder for all writers |

**Verdict: the two designs are COMPLEMENTARY, not either/or.** A guards the moment the flag is SET (a developer who edited files and forgot `git checkout -B` produces verify-only frontmatter; only A's workspace evidence catches that). B guards the moment the flag is CONSUMED (a branch that gained commits after the flag must not ride into Done; only B's live probe catches that — A still accepts on the stale flag today). Merge both:
- **Adopt B's `no-change-completion.server.ts` wholesale** (accept-time gate, in-lock assert, shared event builder, operator wiring). Single-shared-implementation + throws-loudly both favor it. Replace A's inline completion strings with the builder.
- **Keep A's delivery-time mint and the `DefaultBranchEvidence` gate** (pure B has no delivery-door mint at all — B's `performDelivery` only sets the flag on `no_commits`; A's `no_branch`+`neverDelivered` door is what actually un-wedges the VC-5 shape when a human presses Deliver). Keep B's verdict-time mint too — the preconditions are disjoint (B requires no deliverer engaged; both require `!workRevision` with in-lock re-checks, so double-mint is impossible).
- **Schema unification (the load-bearing decision)**: keep B's `kind` field; A's `resolveNoChangeBaseRevision` must stamp `kind: "verified"`. B's docstring contract "a verification revision never carries a task branch (`branch: null`)" collides with A's `branch: defaultBranch` + real `treeSha`. A's shape is more truthful (it names what was judged and treeSha feeds `nextWorkRevision`'s same-tree dedup); relax B's wording to "never a TASK branch" and let `branch` carry the default branch. B's `verdictGateReason`/`rebuilder` arms key on `kind === "verified"`, so they recognize A's mint once stamped. Also update B's schema comment claiming "both minters state the kind outright" — there are three minters after the merge.
- A's `acceptanceBlockedReason` refusal addendum ("run delivery once to verify and record that") stays true and should survive; it is A's answer to the same dead end B answers with the verdict-time mint — belt and braces.

### 2.2 `deriveValidation` staleness (A-UX19-3 vs B-F19-27) — **A's mechanism is stronger; B's arm needs narrowing**
- A: the projection NEVER trusts the cache — `rebuildTaskFile` computes `derivedValidation = deriveValidation(fm)` and ONE derivation feeds the `validation` column AND the projected acceptance gate; plus roster changes re-derive the file cache (`specialist-run.server.ts` mechanisms at engage/remove). Fixes the whole CLASS (any writer that forgets the recompute, hand-edited files).
- B: point recomputes at the two flag writers (`fm.validation = deriveValidation(fm)`), projection still reads the stored value.
- **A wins** (fewer moving parts at the read side; class fix beats point fix). B's writer recomputes are harmless and can be kept, but are redundant under A's rebuilder.
- **⚠ B's new `noChanges → "none"` arm is WRONG under A's model** (semantic collision, see §5.1): in A's flow the verified revision is minted BEFORE the required reviewers approve, so a pending required verdict exists while `noChanges` is true — B's arm would report `none` ("nothing to see") for a task that owes a verdict. B never hits that state (its mint and the approving verdict land in the same write). At merge, narrow the arm: only return `"none"` when no required reviewer verdict is pending (e.g. `fm.noChanges && requiredReviewers(fm).length === 0`, or check pending verdicts explicitly). B's own comment ("only the genuinely empty case — no verdict owed, none given") already states the intended semantics; the code just doesn't enforce it in A's world.
