# UC-17 — Full autonomy + explicit completion grant → Done (merge pending); human merges

## Purpose

Proves the ONE agent exception to human-only Done (FR27/Q1, ruling 20/R15-1 context) and
**R16-6** ("Done" has two meanings):

1. A **full-autonomy** operator holding an **explicit `completion-for-acceptance: direct`**
   grant accepts a verdict-healthy delivered task itself.
2. Raising autonomy alone NEVER confers acceptance — `gate()`
   (`app/server/tasks/operator-actions.server.ts:274-294`) refuses the recommend→direct
   promotion for exactly this capability.
3. The operator acceptance records the PR **`accepted` (merge pending)** and moves the task
   Done — it never merges (merge is attributed to a human; `operatorAcceptCompletion`,
   `operator-actions.server.ts:2017-2133`). Merge-pending must be visible on the **board
   card AND the review queue**, not only task detail (R16-6).
4. A human later completes the real merge ("Complete merge", `completeTaskMerge`,
   `task-actions.server.ts:5331`).

       mode: recommend        # → mode: direct

## Failure signatures (findings)

- Step 1 closes the task to Done → **NEW CRITICAL**: `gate()`'s completion-for-acceptance
  carve-out broken (FR27/Q1 violated — autonomy alone conferred acceptance).
- Step 4: PR merged by the operator (GitHub shows MERGED before step 6) → **NEW HIGH**,
  R16-6 violation (merge must stay human-attributed).
- Step 4 succeeds with `validation != healthy` (e.g. verdict withdrawn mid-run) → **NEW
  HIGH**: operator path bypassed `acceptanceRefusalFor` (R15-1).
- Merge-pending missing from the board **card** view or the review queue → **NEW** R16-6
  finding (list view only = F19-13, already filed).
- "Complete merge" hidden from a contributor-owner (only if probing as EK) → F19-10
  (already filed).
- Operator repeatedly declines to call `accept_completion` at a clean boundary → file as an
  operator-instruction finding against `operatorTurnInstruction` (nondeterminism caveat: one
  refusal is not a finding; a consistent pattern is).
