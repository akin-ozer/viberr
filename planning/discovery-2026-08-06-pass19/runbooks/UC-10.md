# UC-10 — Task ownership: take / assign / release; contributor-owner accepts own task (R6-2)

## Purpose

Proves **FR37** (one human owner = reviewer + acceptance authority, task-scoped, may be
unowned), **FR38** (self-service take/release, admin releases anyone, typed events +
audit), and **ruling 22 (R6-2/R14-2)** — a live contributor-or-higher OWNER may accept
their own task's completion even though `accept-completion` is admin|maintainer. Code
under test (all verified 2026-08-06):

- `setOwner` (`app/server/tasks/task-actions.server.ts:2837-2928`): taking requires
  `own-task` (admin|maintainer|contributor — NOT viewer); handing off requires being the
  current owner or `release-any-ownership` (admin); the target must itself hold
  `own-task`. Idempotent when already owner. Typed `assign` event with exact spec copy;
  audits `task.ownership.taken` / `task.ownership.handed_off`.
- `releaseOwner` (:2934-2993): own seat needs `own-task`; someone else's seat needs
  `release-any-ownership` (admin) — audits `task.ownership.released` /
  `task.ownership.admin_released {forced:true}`.
- `ownerException` (:321-332) + `requireAcceptCompletion` (:335-344): the R6-2 gate.
  Consumed by `acceptCompletion` (:5125), `transitionStage`'s human boundary (:3122) and
  the terminal-stage manual move (:3073-3085 routes `accept-completion` intent through
  the FULL acceptance contract), and `resolveAcceptanceAffordance` (:4984-4986 — the UI
  Accept affordance carries the same owner exception).
- Route intents (`app/routes/project.task.tsx`): `owner-take` (:508), `owner-assign`
  (:520, field `userId`), `owner-release` (:537), `accept-completion` (:431).

## Expected outcomes (PASS evidence)

- The authority flip in steps 1→4: 403 (non-owner contributor) → acceptance-gate
  refusal (owner) with **zero state change** either time; VC-5 never leaves `review`.
- Every ownership mutation writes BOTH a typed `assign` timeline event with the exact
  §5.2 copy above AND its audit row with previous/new owner ids (FR38).
- Viewer take → 403; viewer as hand-off target → 403; contributor take-over of a held

  Arda owns, expect `release-any-ownership` refusal).

  visibility tracks `hasAuthority` per viewer.

## Failure signatures (findings)

- Step 4 still 403s with Elif as owner → **NEW HIGH**: R6-2 regression (the review
  queue's promise breaks — `requireAcceptCompletion` owner exception dead).
- Step 4 ACCEPTS/merges/moves to Done with no revision → **NEW HIGH**: R15-1
  verdict-gate bypass (worse than F19-3/F19-7 — those skip a dialog, this would skip
  the gate).
- Step 2 or 6 succeeds for a viewer → **NEW HIGH**: `own-task` tier widened.
- A contributor releases someone ELSE's seat → **NEW HIGH** (`release-any-ownership`
  widened beyond admin).
- Missing typed event, wrong copy, or missing audit row on any mutation → **NEW MED**
  (verbatim-copy contract, ruling 14 / FR38 audit).
- Owner-flip does not update the review queue / "Waiting on you" scoping → **NEW MED**
  (R8-3 member-scoped attention reads ownership).
- If the full-merge variant runs: contributor-owner sees no "Complete merge" control on
  a merge-pending task → **F19-10** (filed — record repro, don't re-file); accept via
  rec-Apply/packet skips the dialog → **F19-3/F19-7** (filed).
