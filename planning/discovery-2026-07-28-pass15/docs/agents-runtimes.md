# Code map: generic agents + runtimes (pass 15, 2026-07-28)

Scope: agent profiles, engagements, capability grants, tool confinement, the two SDK adapters, outcome envelopes, resume, skills/KB/MCP mounting, injection guardrails, mention notification, and the fake test runtime. All statements describe observed code behavior.

## 1. Profiles: uniform machinery + two layers

- Two-layer model: org template files `${dataRoot}/agents/profiles/<id>.md` + per-project deployments in `project.md agents:` (`app/features/agents/agents-query.server.ts:26-39`). The effective profile merges template fields with the deployment's loose `definition` override, per field (`effectiveProfileView`, agents-query.server.ts:223-301). Project-created profiles carry their full definition in the deployment and have no template (`source: "project"`, :299).
- Kinds: `operator` and `specialist` only — reviewer is not a kind (generic-agents G1). All non-operator profiles are one machinery differentiated purely by capability grants + resources + persona.
- Backend selection: first runnable backend in `view.backends`, defaulting to claude (`pickBackend`, `app/server/tasks/specialist-run.server.ts:131-134`). Model labels resolve through `resolveRunModel` so display labels never hit the SDK (:145-147).
- Capability policy always comes from the DEPLOYMENT (`deployment.capabilities`), never the template — the view coerces specialist `recommend`→`direct` for display only; runtime reads the raw deployment grants (agents-query.server.ts:233-245).
- Empty deployment grants (`capabilities: []`) resolve to the fully-WITHHELD set with a log warn (`deploymentGrants`, specialist-run.server.ts:172-182; `withheldAgentGrants`, `app/features/agents/capability-catalog.ts:90-95`) — P13-AP-06 closed the "empty list = full power" hole.

## 2. Engagements: task-scoped

- Engagements live in `task.md` frontmatter `engagements[]`: `{profileId, backend, role, delivers, verdictCapable}` (`app/schemas/task-file.schema.ts:119-135`). Exactly one `delivers: true` entry (the deliverer); the rest are supporting. Legacy `specialist`/`reviewers` keys are absorbed on read and re-emitted as `engagements` (:736-752).
- `verdictCapable` is an ENGAGE-TIME snapshot of `resolveAgentCollab(grants).verdict` (specialist-run.server.ts:353, :473). Required reviewers = supporting engagements with `verdictCapable` (task-file.schema.ts:498-499).
- Stage eligibility is profile-scoped (`stages`/`spanAll`), enforced at assign AND run boundaries against the project board (`assertStageEligible`, specialist-run.server.ts:1687-1704, called at :295, :432, :712).
- Guards: swapping the deliverer while its run is live is refused (P14-GV-10, :306-322); one live delivering run per task (single-flight, :629-646, plus a DB unique-constraint backstop in `run-service.server.ts:336-350`); duplicate profileIds in engagements are prevented because run routing takes the first `engagements.find` match (:341-358).
- Runs follow the LIVE deployment, not the engage-time snapshot (backend/model/effort re-resolved each run; the snapshot backend is rewritten after a switch, :649-706, :925-936). `backendOverride` implements D4 retry-on-other-backend; cross-backend retries re-resolve model/effort for the actual backend (:697-706).

## 3. profileId actor identity

- The agent's actor ref is `{kind:"agent", backend, profileId, roleHint}` — profileId is the identity, role is display (`agent-reply.server.ts:127-135`; used for toolkit writes at specialist-run.server.ts:742-747). Audit rows for agent comments/packets are attributed to the encoded agent ref, not the operator (P11-23, `agent-toolkit.server.ts:109-117`, :181-190).
- Git identity is forced to `{name: profileId, email: profileId@viberr.local}` via GIT_AUTHOR/COMMITTER env (F24, specialist-run.server.ts:1475-1487) and repo-local `git config` at clone (:1502-1511). On Codex the env only reaches the model's shell via `shell_environment_policy.set` (`codex-runtime.server.ts:154-169` — P13-RT-10).

## 4. Capability grants model

- Catalog: `UNIFIED_CAP_CATALOG` (`app/shared/capabilities.ts:33-98`) — operator coordination caps, agent delivery caps (headline `execute-code-or-write-repo` + scoped branch/commit-push/open-PR), collaboration caps (comment/ask/verdict/evidence/web), matrix-only advisory caps (`group: null`), and always-human locks. `defaultGrantsFor` (:109-116) vs `conservativeGrantsFor` (:130-140, delivery withheld — used where no capability UI exists, e.g. org templates).
- Polarity (P14-LV-01): for the delivery + verdict set (`GRANT_REQUIRED_CAPABILITY_IDS`, `specialist-tool-policy.ts:102-109`), ABSENT means WITHHELD. `isWithheld` (:137-145): always-human → withheld; explicit `human`/`off` → withheld; undefined → withheld only for grant-required ids (non-delivery caps keep the permissive default).
- `normalizeDeliveryGrants` (capabilities.ts:234-267) repairs a headline that is ABSENT **or explicit `off`** to `direct` whenever any scoped delivery grant is actionable; explicit `human` is respected. Applied at SAVE time only: edit path `grantsFor` (`agent-profile-actions.server.ts:182`), create path `createModalGrants` (:225), library deploy (:395-398), and the seed (`agent-catalog.server.ts:186`).
- It must NOT be applied at the enforcement layer: `grantModes` (specialist-tool-policy.ts:127-135) repairs ONLY the absent headline, and deliberately never reinterprets an explicit `off` (docstring :111-126) — otherwise a scoped grant would silently overturn an admin's explicit withholding.
- Enforcement metadata: `ENFORCED_CAPABILITY_IDS` (both backends), `CLAUDE_ONLY_ENFORCED_CAPABILITY_IDS` (branch/commit-push/open-PR/comment-on-task bind on Claude only), `capabilityEnforcement()` (capabilities.ts:160-217).

## 5. Tool confinement + prompt parity

- `CAP_DENY_RULES` map withheld caps to Claude denylist entries (specialist-tool-policy.ts:47-95): branch (`git checkout -b/-B`, `switch -c/-C`), commit+push, `gh pr create/merge`, headline → `Edit/MultiEdit/Write/NotebookEdit/Bash(git commit:*)`, web → `WebFetch/WebSearch`. Shell writes (`sed -i`, redirection) stay reachable — documented tension, Bash is needed for validation.
- `resolveSpecialistDisallowedTools` (:151-162); `resolveUndeployedDisallowedTools` (:176-180) is the everything-withheld posture for a run whose profile can't be resolved — used as the BASELINE in `startAgentRun` (specialist-run.server.ts:688) and in the resume fallback (:1439), fixing P14-RT-01 (undeploying used to escalate a Codex run to `danger-full-access`).
- `resolveDeliveryPermissions` (:194-213) keeps the PROMPT consistent with enforcement (XS-4): headline withheld gates all three steps; `buildAnalyzePrompt` emits explicit prohibitions instead of silent omissions (specialist-run.server.ts:1191-1217). Supporting runs get a read-only contract regardless of grants (:1182-1190).
- Codex has NO denylist channel ("Codex-ignores-disallowedTools"): the flags `repoWriteWithheld`/`webSearchWithheld` are DERIVED from the denylist markers in `startRun` (`run-service.server.ts:260-295`, :400-411) → read-only sandbox (P13-RT-02) and `webSearchMode: "disabled"` (P14-RT-06). Everything finer-grained (branch/push/PR, comment-on-task) is prompt-advisory on Codex.

## 6. Claude adapter (`app/server/runtimes/claude-runtime.server.ts`)

- Official Agent SDK; streaming-input single user message enables `interrupt()` (:257-265). `permissionMode: bypassPermissions` when autonomous (:513). Denylists compose: `BASE_DENIED_BUILTINS` for every run (Skill, Task* family, Workflow, Cron*, notification/worktree tools — :227-255), + operator set (:163-171), + supporting-run set (read-only, :186-199), + per-spec capability denylist (:579-586).
- Isolation: `settingSources: []`, `skills: []`, `plugins: []` (:535-537). Honest limit: ~16 first-party skills are compiled into the SDK binary and still LISTED in init; only the `Skill` tool denial makes them uninvokable (:527-534).
- System prompt: operator persona REPLACES the default; specialist persona is APPENDED to the `claude_code` preset (:554-564).
- Guards: idle timeout 15 min (P13-RT-11, :150-155), turn cap default 2000 (:329-334) with `max_turns` classified as cut-off not failure (:659-674). Failure classification is redaction-safe with a `·<kind>` tag suffix (quota/auth/session_missing/unknown, :336-390); an `is_error` RESULT is classified too (P14-RT-10, :675-698).
- Live usage accumulation from assistant messages; final result envelope is authoritative (:591-631).

## 7. Codex adapter (`app/server/runtimes/codex-runtime.server.ts`)

- Sandbox: operator + reviewer → `read-only`; delivering with repo-write withheld → `read-only`; else `danger-full-access` when autonomous (`resolveCodexSandboxMode`, :267-272). `approvalPolicy: "never"` (:512).
- Config isolation (`codexConfigForRun`, :189-253): `developer_instructions` carries the persona; `project_doc_max_bytes: 0` (repo AGENTS.md never read — RT-04); skills channel fully disabled; `features.apps/plugins/hooks: false`; memories off; `mcp_servers` replaces only per-leaf keys — the app-owned CODEX_HOME (`prepareCodexHome`, re-mirrored per run in `selectAdapter`, `runtime-registry.server.ts:342-351`) is what makes isolation exhaustive.
- MCP translation (:83-122): portable HTTP/stdio only; in-process `{type:"sdk"}` servers skipped; credentials DELIBERATELY DROPPED (they would be `ps`-visible in `--config` argv) — a credentialed org MCP authenticates on Claude only. Vendor naming skew: Codex lowercases hyphens to underscores in tool prefixes (disclosed, not normalized, :74-79).
- Env: the SDK REPLACES the child env; per-run env overlays a complete filtered base (:463-485); only `SHELL_EXPORTED_ENV_KEYS` (git ceiling + identity) reach the model's own shell (:154-169). Success = `turn.completed` with no top-level `turn.failed`/`error`; item-level errors are non-fatal (:552-569). Same 15-min idle guard and redaction-safe failure classes (:274-366).
- Availability: cheap credential-presence probes, re-run every call (self-healing docker auth.json trap), sticky test overrides (`runtime-registry.server.ts:118-176`). Both spawn envs strip `CREDENTIAL_ENV_RE`-shaped vars (:199-213).

## 8. Outcome envelope + fallback parsing

- One envelope shape (`AgentOutcome`: summary/verdict/question/evidence), two transports (`agent-outcome.server.ts:14-30`): Claude stages via the `report_outcome` toolkit tool (keyed by `outcomeKey`, persisted in `staged_outcomes` for restart survival, :208-263); Codex constrains the FINAL reply with `AGENT_OUTCOME_JSON_SCHEMA` (:61-123, OpenAI-strict: all fields required, optionals nullable). Envelope mounted on Codex only when verdict/ask/evidence is granted (specialist-run.server.ts:881-884), so a plain developer replies in prose.
- `parseAgentOutcomeJson` (:131-195): tolerant (strips one fence); an envelope with only evidence is NOT an envelope (:192-194).
- Completion (`applyAgentCompletionEffects`, `task-actions.server.ts:2015-2400`): staged outcome first, then Codex JSON parse of the stored reply (:2105-2114); raw JSON never becomes the timeline comment. Verdict authority = engage-time `verdictCapable` snapshot, falling to live grants only without an engagement row (F10-15, :2093-2102); question authority = LIVE `ask` grant (deliberate asymmetry, P11-26, :2147-2155); evidence gated on live `attach-evidence-references` (:2161-2164). A verdict-authorized agent with no envelope falls to the prose classifier; the regex never runs without authority (R1, :2117-2146); no determinable verdict → validation left unchanged + loud warn.
- Errored runs: typed blocked event + stuck-loop packet with a `retry_other_backend` option for quota/auth/unavailable (:2188-2283). No-progress (verbatim repeat) and react-depth caps open stuck packets; `clearWaitingToHuman` always flips waiting off `agent` (:2356-2393).
- Collab gates: `effectiveCollabMode` — explicit grant wins except `recommend` (falls to catalog default, deliberately NOT coerced here, :300-321); defaults: comment/ask/evidence on, verdict off.

## 9. Resume behavior

- `resumeRun` (`run-service.server.ts:599-718`): new run row, fresh derived thread id, provider `session_id` carried. Pre-flight `probeSessionContinuity`; `missing` → records session-missing, notes a continuity reset, starts a FRESH run with a re-anchor preamble and NO resumeSessionId (:650-685). Both adapters also classify `session_missing` if the SDK finds out first.
- `resolveResumeConfinement` (specialist-run.server.ts:1341-1441) re-applies denylist, env, MCPs, persona, and the collaboration transport (Claude toolkit with a new outcomeKey / Codex envelope schema — F7 parity). Unresolvable profile → fully-withheld denylist.
- @mention flow (`commentToAgent`, task-actions.server.ts:929-1200): resolve target → append comment → RBAC (lower roles comment but trigger nothing) → `@operator` routes to a governed operator run; existing session resumes with `specialistReplyDirective` (canonical task anchor + trust boundary + delivery rule, :892-926); no session → fresh run with `directive`/`directiveFrom` (P14-RT-02). Session matching requires profileId + engagement kind + backend and skips proven-dead sessions (`latestSessionRun`, agent-reply.server.ts:185-207; rows are ASC, the backwards loop is correct per run-store.server.ts:191).
- Resumed runs use the profile's CURRENT model/effort, not the prior row's (:1085-1097).

## 10. Skills, KB, MCP mounting

- Persona assembly (`buildSpecialistPersona`, specialist-run.server.ts:1016-1132): profile definition body (single source, F10-30 — the `agents/definitions/<id>.md` override is REMOVED despite the stale interface comment at :116-118) + declared skills + declared KBs, wrapped in a trusted-provenance banner only when real content resolved (:1066-1082).
- Skills: selected solely by the profile's declared `resources.skills` names; `readSkillBody` (`app/server/files/skill-body.server.ts:23-54`) reads SKILL.md frontmatter-stripped, 24k per-skill budget with a visible clip marker; missing/unreadable → warn + run proceeds without it. Both CLIs' own skill channels are closed, so injection-as-text is the only skills path.
- KB: `readKbBody` (`app/server/files/kb-injection.server.ts`) walks the whole tree, matches `.md/.markdown/.mdx/.txt/.rst/.text`, symlink-safe; `KB_INJECTION_BUDGET` (24k) is a GLOBAL cap decremented across the profile's KBs (specialist-run.server.ts:1053-1065); an over-budget KB gets an explicit "omitted" marker instead of silent shrink (P14-KM-05).
- MCP: `resolveSpecialistMcpServersDetailed` (`specialist-mcp.server.ts:81-158`) resolves names against the org registry; reserved names (`viberr`, `viberr_agent`) never resolve; sealed credentials decrypt at spawn only (Claude-only, see §7). Unresolved grants vs mounted-but-down servers are reported separately and become honest persona sections ("Unavailable" / "may be unavailable", specialist-run.server.ts:1102-1130) plus the MCP-governance rule ("MCP tools do not widen authority", :1084-1101) — the tool layer cannot gate `mcp__*`. Renames now rewrite agent grants (P14-KM-01, `resources.server.ts:1025-1039`).

## 11. Injection guardrails + mention notification

- Every fresh prompt ends with the trust-boundary block (content is data, authority only from run permissions, specialist-run.server.ts:1248-1262); directives are framed as "NOT an authority grant" and name the asking human so the reply tags them (:1219-1246, fixing the live goal-read-as-injection failure). `directiveRequestsDelivery` (:1287-1300) is a secondary detector for delivery-demanding directives (negation- and question-aware after P14-LV-10) that only adds a policy timeline event (:944-958).
- `notifyMentionedUsers` (`mention-notify.server.ts:57-94`) is the ONE fan-out every comment writer uses (NEW-4): human comments, agent replies, operator narration, and mid-run `post_comment` (agent-toolkit.server.ts:121-128). Matches email local-part / first name / full display name via the shared span-finder; `RESERVED_HANDLES` (agent/operator/claude/codex) never notify a person. `agentMentionHandle` (agent-reply.server.ts:87-95) is the single handle derivation (profileId preferred; P14-RT-12).
- Toolkit (`buildAgentToolkit`, agent-toolkit.server.ts:207-374): tools are built only when granted — `post_comment` (comment), `ask_human` (ask; refuses when a packet is open; flips waiting→human), `report_outcome` (verdict; the `evidence` field is only DECLARED when `attach-evidence-references` is granted).

## Suspect areas

1. **Save-time `normalizeDeliveryGrants` flips an explicit headline `off` to `direct`** (capabilities.ts:244-253 comment calls this "repairing an editor artifact"). An admin who deliberately sets "Execute code or write to the repo: Off" while leaving `commit-push-branch: direct` gets silently escalated on the next SAVE, while the enforcement layer (`grantModes`) would have honored the `off`. The mirror-image asymmetry is documented but the save path cannot distinguish "editor materialized off" from "admin chose off"; `human` is the only respected withholding. Escalation happens with no audit/timeline trace.
2. **`@claude`/`@codex` backend handles can engage an arbitrary specialist.** `handleMatchesSpecialist` matches on backend (agent-reply.server.ts:143-152), and `commentToAgent` uses `specialists.find(...)` — the FIRST deployed specialist of that backend in project.md file order — then, if a primary exists, ENGAGES it as a reviewer and runs it (task-actions.server.ts:1142-1167). On a project with several claude-backed profiles, "@claude please look" deterministically picks whichever is listed first, which may be a profile never intended for this task; the fallback at agent-reply.server.ts:318-341 (primary-of-that-backend) is only reached when NO deployed specialist matches.
3. **Evidence-granted Codex agents get the envelope schema but no prompt instruction for it.** `useEnvelopeSchema` includes `collab.evidence` (specialist-run.server.ts:881-884), but the Codex collab note (:827-834) is only emitted when `collab.verdict || collab.ask` — an evidence-only Codex profile has its final reply forced into the JSON envelope with no prompt text explaining the shape (only schema descriptions), risking degraded prose reports.
4. **Undeployed-profile runs keep permissive collaboration defaults.** `startAgentRun` resolves `collab` from `resolved?.capabilities ?? []` (:740), and `resolveAgentCollab([])` yields comment/ask/evidence = on (catalog defaults). So a run of a vanished profile is fully tool-withheld for delivery (correct, P14-RT-01) yet still mounts `post_comment`/`ask_human` and can open question packets. Completion-time `question` gating also passes (live grants unresolvable → defaults, task-actions.server.ts:2071-2084). Possibly intended ("non-delivery caps keep the permissive default"), but it diverges from the "we can confirm nothing about this profile" posture used for tools.
5. **Stale interface comment**: `ResolvedSpecialist.definition` still says "a shipped agents/definitions/<id>.md still overrides it" (specialist-run.server.ts:116-118) while `buildSpecialistPersona` (:1033-1037) documents that override as REMOVED (F10-30). Code follows the latter; the former misleads.
6. **`comment-on-task` withheld is advisory on Codex but nothing tells the Codex run.** On Claude the tool simply isn't mounted; on Codex there is no mid-run comment channel at all, so the capability is moot — but the capability matrix's "claude-only enforced" labeling (capabilities.ts:196-204) is the only surface where that asymmetry is visible; no persona text mentions it.
7. **Directive-delivery detector scans only 60 chars of lead context per clause** (specialist-run.server.ts:1290-1296) — a negation more than 60 chars before the phrase inside one clause re-triggers the false-positive policy event class P14-LV-10 fixed. Low stakes (secondary nudge only), but the same live failure mode.
8. **`webSearchWithheldFromDenylist` and `repoWriteWithheldFromDenylist` key off exact marker strings** (run-service.server.ts:260-295). If `CAP_DENY_RULES` ever renames/extends its deny entries (e.g. adds a tool to the headline rule), the marker sets silently stop matching and Codex enforcement quietly drops while Claude keeps working — a drift hazard with no test tying the two constants together across files (worth verifying coverage).

## Open questions

1. Should an explicit headline `off` + actionable scoped delivery grants be treated as admin intent (respect the off, warn in the editor) rather than silently normalized to `direct` at save? (Suspect 1 — pick one polarity for save and enforcement.)
2. What should `@claude`/`@codex` mean on a multi-specialist project — the engaged agent of that backend, the primary if it matches, or an error asking for a name? Auto-engaging the first deployed profile of that backend seems unintended.
3. Undeployed/vanished profiles: should collaboration (ask_human, post_comment) be withheld along with delivery, matching the "confirm nothing" posture, or is asking-a-human exactly what a stranded run should do?
4. Codex evidence-only envelope (Suspect 3): add a prompt instruction, or require verdict/ask for the envelope and route evidence-only agents through prose?
5. `comment-on-task` on Codex is unenforceable and unusable (no channel) — should the profile editor hide/disable the toggle for codex-only profiles instead of offering a no-op?
6. The seeded persona/`definition` is the only persona source now; is a per-project persona override on top of an org template (deployment `definition.persona`) the intended long-term authoring story, or should template edits propagate to deployed copies (they currently do for template-sourced profiles, but library-deploy copies freeze grants)?
