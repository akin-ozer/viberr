# Lens 1 — does Viberr enforce what it tells agents it is enforcing

Branch `pass38/airbnb-clone-fixes`, read-only sweep, 2026-09-18. Shape hunted: ruling 186 (a prompt ASKED where a gate was needed) and ruling 240 (a prompt CLAIMED a gate nobody built, or gated one door while the harm went through another).

Method: grepped the enforcement vocabulary across every agent-facing builder (`specialist-run`, `operator-run`, `controller-run`, the three toolkits, both MCP mounts, `strict-tool`, `bash-policy`, `specialist-tool-policy`, the five seeded `.md` assets) — 1,113 hits, 561 in string literals — then traced each asserted gate to code and walked every door it must cover. `holdRefusal` has exactly four server call sites; `leaseConflictFor` has one; every `startAgentRun(` caller was enumerated (10) and every `performDelivery(` caller (3).

## Ranked findings

1. **(MEDIUM, #6) A deliverer whose `commit-push-branch` is withheld is told the server will publish its uncommitted edits. Nothing does.** Scenario: profile with `execute-code-or-write-repo: direct` and `commit-push-branch: human`. On Claude `Bash(git commit:*)`/`Bash(git push:*)` are denied (tool-policy:68), Edit/Write are not; the agent edits, cannot commit, and reports "files + summary" as instructed (specialist-run:3167). The operator calls `deliver_for_review`; `resolveDeliveryPushGrant` reads that same profile and answers false (task-actions:6725-6745), the push returns `grant_withheld`, the operator sees "Delivery did not complete" (operator-actions:3594). Even a human pressing Deliver meets `changedFilesForPush`'s dirty-tree failure (push-workspace:518-526). The sentence promises a door that is closed on both sides; the work is stranded in a workspace that the retention sweep will dispose of (ruling 187's own shape). Same on Codex, where the agent CAN commit (advisory) but the server still refuses the grant. Fix shape: the prompt should say the truth — "your profile cannot deliver; report the diff in your reply" — or the grant model should not allow write-without-commit for a delivering engagement.

2. **(MEDIUM, #15) File leases are enforced on the push's delta, not on the branch, and never at the merge.** `changedFilesForPush` measures `remoteHead..HEAD` (push-workspace:330-358). Scenario (the live SHOP-19/SHOP-5 ordering): task B pushes a `pnpm-lock.yaml` change at t0; at t1 an admin declares the lease for A; at t2 B pushes a docs fix — the range holds no lockfile, the push passes, B is accepted and the acceptance ceremony (no lease read anywhere in it) merges B's lockfile ahead of A. The `set_file_leases` text "another task whose push changes a leased path is refused by name" is narrowly true and the `get_project` promise "which task owns which shared paths until it merges" is not. Two more gaps: `null` from git "refuses nothing" (:942-946), and the base-refresh push at update-branch.server.ts:557 bypasses the gate entirely.

3. **(MEDIUM, #2) Ruling 241 was applied to one packet arm; two more still consume the decision before the hold refuses.** `resolve_remote_collision` on a held task closes the squatting PR and deletes the stale remote branch (task-actions:10650-10660), then `manualDeliverForReview` meets `holdRefusal` (:7017) and the note reads "The stale remote branch was cleared, but the re-delivery did not complete" — the packet is gone, the destructive half happened, the promised third step did not. `retry_other_backend` resolves the packet, then `startAgentRun` throws the hold (:11239-11265, "The retry could not start"). `force_accept`'s own comment states the rule these break: run every refusal "before the resolution write".

4. **(LOW, #14) The controller is handed a route that does nothing.** Its guide says "To push a task forward, prefer `comment_on_task` with a clear @operator directive" (controller-guide.skill.md:48) while its tool says "a comment starts no run" (controller-toolkit:1929) and the code agrees (`postAgentComment`, no mention dispatch). A person's `@operator` comment does start a run (task-actions:1936), so the definition's absolute "whoever it mentions" is also false as a statement about the product. Scenario: the controller posts "@operator deliver SHOP-4", reports the task as pushed forward, and nothing runs.

5. **(LOW, #4/#1 door) The hold gates dispatch and delivery, not stage moves or the base refresh.** A held task can be moved by the controller's `move_task`, the board, or a `move_stage` option, and `update_branch_from_base` pushes merge commits to its branch. None is claimed as refused, so no prompt lies, but ruling 186's "the words on the board become true" stops at the two doors.

6. **(LOW, #17/#5) "refused however it is wrapped" overclaims; the real fence is the credential-less workspace.** bash-policy says so itself. It matters only if a run's HOME could carry a `gh`/git credential store — I could not verify that it cannot from the code read (the spawn env is stripped; the per-person `claude-home`/`codex-home` contents were not inspected).

7. **(LOW, #16) Declared path sets have no gate anywhere.** Any task goal saying "Viberr refuses changes outside these paths" is unbacked; only admin-level project leases (#15) look at paths, and only on push deltas.

8. **(LOW, #8/#11/#21/#25) Wording drift**: MCP write tools named natively while Claude denies the mangled id; the operator definition calls a Codex-writable tree "read-only"; a delivery directive is "treated as guidance" but reaches the agent unchanged; "tools will not take" secrets is true of declared fields, not of `args`/`url`.

## What held (adversarially re-checked)

Ruling 186 + 240 are complete at their two doors: every one of the ten dispatch callers and three delivery callers lands on a gate that reads the live `blockedBy`, including scheduled fire (schedule.server.ts:653), the abandoned-wait sweep and restart recovery (both re-invoke the operator, whose dispatch is gated), the controller (throws → its `run` guard relays it as `[error] … is refused`), and the task page. Ruling 176's MCP denials reach both adapters for specialists and both operator backends. Ruling 101(e)'s hook is wired exactly as described (Claude only). Always-human capabilities are enforced at the operator tool (reroute to acceptance), at the controller (no tool; `move_task` refuses terminal), at the Claude tool layer (`gh pr merge` denied), and, on every backend, by the absence of any GitHub credential in the run. `github_read` is GET-only. Unknown tool arguments are refused, not stripped.

Unverified in this sweep: #27, #28, the dependency release engine, per-engagement workspace isolation, the run HOME's credential contents, and the SDK's MCP name mangling.
