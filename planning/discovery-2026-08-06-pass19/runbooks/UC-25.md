# UC-25 — Commit pushed to the PR head AFTER review → divergence surfaced on accept (R17-1)

## Purpose

Proves **R17-1 / ruling 42** (acceptance MAY accept a head strictly AHEAD of the reviewed
revision but MUST surface the divergence pre-decision, name the ACTUAL merge head in the
completion record, and still REFUSE a head that *diverged*). Mechanisms under test:

- Drift recording: `reconcileTask` (`app/server/github/github-reconciler.server.ts:299-330`)
  — for an OWNED, live `review|accepted` PR whose head ≠ `workRevision.headSha`, one extra
  compare call; a clean `"ahead"` writes `pr.revisionDrift: {aheadBy, headSha}`
  (schema `task-file.schema.ts:326-339`). A *diverged* head records NO drift (that case is
  the acceptance REFUSAL, not a warning).
- Pre-decision surfaces: accept/force dialog "Merge head" warn row
  (`app/features/task-detail/accept-confirm.tsx:105-121` — "<sha12> — N commit(s) added
  since review; they merge unreviewed"); review-queue subline
  (`app/features/review/review-helpers.ts:49-52` — "PR #N is open — N commit(s) added since
  review would merge unreviewed.").
- Post-decision record: `revisionDriftNote` (`app/server/tasks/task-actions.server.ts:5030`)
  appended to EVERY acceptance completion event ("N commit(s) were added to the PR head
  (`<sha12>`) after the review — outside the reviewed revision."); the real merge sha lands
  in the `github.pr.merged` audit row.
- The refusal boundary: `acceptancePrHeadMismatch` (`task-actions.server.ts:4851-4898`) —
  identical or `ahead` (containment) passes; anything else refuses, and force-accept can
  NEVER bypass it (A2).

**Standing live evidence (2026-08-06, VC-4)**: reviewer approved revision `81894e7`; an
out-of-band commit `a4c790c` was pushed; reconcile recorded
`revisionDrift {aheadBy: 1, headSha: a4c790ce63ef…}`; the task-page accept dialog rendered
the full R17-1 disclosure (MERGE HEAD row, warn tone); PR #150 then merged for real at
`bde64bb` — but via the **rec-Apply path with NO dialog at all** (**F19-3, HIGH, filed**),
and the completion event misprinted "1 commit **were** added" (**F19-23, LOW, filed**).
This runbook re-proves the chain on a fresh task and re-records those two known findings.

## Steps

1. **Push a commit to the PR head, out-of-band** [API] — server-side via the contents API

## Failure signatures (findings)

- No `revisionDrift` after step 2 on a clean-ahead head → **NEW HIGH** (R17-1 recording
  dead; check the reconciler's extra compare call :317-329).
- Dialog lacks the "Merge head" row while task.md carries `revisionDrift` → **NEW HIGH**
  (accept-confirm regression).
- Queue subline shows the generic "open for review" line while drift exists (and
  blockReason is null) → **NEW MED** (`review-helpers.ts:49-52`).
- Acceptance REFUSES a clean-ahead head → **NEW HIGH** — the owner ruling explicitly keeps
  "ahead" acceptable; refusing it re-litigates R17-1.
- Diverged head ACCEPTED (step 7) → **NEW CRITICAL** (`acceptancePrHeadMismatch` bypass —
  F15-15 class).
- Completion event omits the drift suffix, or audit lacks the real merge sha → **NEW MED**.
- Rec-Apply / packet accept with no dialog → **F19-3 / F19-7 (filed)**; "1 commit were
  added" → **F19-23 (filed)**. Record repros only.
- Reviewer verdict silently invalidated by the ahead push (verdicts dropped without a new
  revision) → **NEW MED** (`nextWorkRevision` same-subject contract).
