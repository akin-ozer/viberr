### U35-5  The review queue sees only the stage before Done; on a custom board the review stages are invisible

**Root cause.** `app/server/projections/review-queue.server.ts:149` (and the doc comment at `:22`) picks rows as non-archived tasks whose `stage === resolveStageRoles(project.stages, project.workflow).reviewId`; `app/shared/workflow/stage-roles.ts:41-70` defines `reviewId` as the first stage with an edge INTO the terminal stage (fallback: the stage positionally before it). On the default board that is Review; on this board (`triage, design, impl, validation, review, merge, done`) it is **Merge**, so a task at Validation with an open PR and an engaged reviewer, or at Review, is not a row at all. The page then prints "0 tasks at the review boundary · 0 waiting on your acceptance" and the empty-state "No review work in flight" (`app/features/review/review-page.tsx`) while eight PRs are under review. Only the `ready` half of the queue (acceptance) is genuinely about `reviewId`; the `working` half ("Still in review") is about review work, which the board defines by engagements and verdicts, not by a stage id.

**Fix.** Keep `ready` rows as they are (tasks at `reviewId` whose acceptance is not blocked). Redefine `working` rows as every non-archived, non-terminal task that satisfies any of: (a) `stage === reviewId` and not `ready`; (b) `pr.state === "review"` with an open pull request (`pr.number` set); (c) at least one engagement with `verdictCapable: true` whose verdict on the current work revision is missing or `request_changes` (`validation` in `changed | failing`). Compute (b) and (c) from the projection row (`pr_json`, `reviewers_json`, `validation`, `work_revision_sha`) so the query stays one pass. Subline copy per row: `Review in progress at Validation · PR #8 · awaiting verdict` / `· changes requested`. Header count sentence becomes `N in review · M waiting on your acceptance` (drop "at the review boundary", which named the stage the rows no longer share). Empty state unchanged in wording but now true. Docs: `docs/ui/surfaces.md` review queue row and `docs/domain/task-lifecycle.md` §20 (the queue's membership rule).

**Tests.** `app/server/projections/review-queue.server.test.ts` (extend the existing custom-board fixture or build one with `stages: [..., validation, review, merge, done]`): a task at `validation` with `pr: {number: 8, state: "review"}`, a `verdictCapable` engagement and `validation: "changed"` appears in `working` with the subline naming Validation and PR #8; a task at `impl` with no PR and no reviewer does not; a task at `merge` with a healthy verdict is `ready`. Break: restore the `t.stage === reviewId` filter for the `working` half -> the Validation row disappears -> red. `app/features/review/review-page.test.tsx`: the header renders `8 in review · 0 waiting on your acceptance` for such a fixture.

**Validate live.** `/projects/k9c-k9s-clone/review` lists KNC-8/9/18/19/20/23/28/30 under "Still in review" with their PR numbers; the sidebar badge counts them; the home "waiting on you" numbers are unchanged (they read the `ready` half).

**Blast radius.** `getReviewQueue` callers: `app/routes/project.review.tsx`, the workspace rail badge (`app/features/shell/nav.ts` or the project loader that counts the queue: grep `getReviewQueue`), Home decision counts (`decisionsRequiring`, must keep reading `ready` only). e2e: `01-home-board` (queue badge), any spec asserting the review queue's empty state.

**Slice.** New slice S10 (review queue): `app/server/projections/review-queue.server.ts` (+test), `app/features/review/review-page.tsx` (+test), docs above. Parallel with everything except S9. No ruling needed: the page's own subtitle already promises the behaviour.
