# Glossary

> The vocabulary the code, the UI and the rulings use. Where a term has an enum behind
> it, the enum is the truth and is named.
> Source of truth: `app/schemas/task-file.schema.ts`, `app/schemas/project-file.schema.ts`,
> `app/schemas/epic-file.schema.ts`, `app/shared/*`, `db/migrations/0001_baseline.sql`,
> and the modules named per entry.
> Verified against `main` @ `7d9fbf72` (2026-09-23).

**Acceptance** — the human act that closes a task into the terminal stage. Verdict-gated and refused while the PR is closed unmerged (ruling 95), requires the review PR head to contain the delivered revision (ruling 96), and must carry the disclosure echo the human was shown (ruling 97). When the reviewed head is behind its base, the accept dialog offers "update the branch and re-review first" (`refresh-and-review`, ruling 97). Two other endings exist: **force-accept** (admin-only override of the verdict gate, audited `task.acceptance.forced`, recorded as `acceptance: forced` and rendered `bypassed`) and **Completed, no changes** (a verified empty diff or no branch; still verdict-gated, merges nothing).

**Actor reference** — how a file names who did something: `user:<id> (Name)`, `agent:<backend>/<profileId>`, `operator`, `controller`, `system:<id>`. Codec in `app/server/files/actor-ref.server.ts`; an unrecognised ref decodes to `unknown` and re-encodes verbatim.

**Agent account** — one of a person's connections to one backend, on Profile → Agent accounts (ruling 137). A person may keep several per backend, up to ten (ruling 138): one row each in `user_backend_credentials`, and exactly one of them **active**, the one their runs on that backend bill (the most recently connected or switched to). Connecting adds an account; **switching** makes another one active without a sign-in; disconnecting removes one. Three `kind`s: `login` (a hosted sign-in run by the unmodified vendor binary; the credential file lives in that account's own home under `runtimes/users/<userId>/`, and Viberr holds no secret at all), `api_key` and `access_token` (a pasted value, sealed, shown only as its last 4 characters; Claude takes `api_key`, Codex `api_key` or `access_token`). `method` records which vendor flow signed in: `claudeai | console | device`. An account may carry the person's own name (`label`).

**Agent profile / template** — an org-level markdown file `agents/profiles/<id>.md` describing an agent: `kind` (`operator | specialist | controller`), backends, model, effort, eligible stages (`stages` / `spanAll`: where the profile may be **newly engaged** on a task, resolved per board by R14-1's three steps; ruling 181), resources (skills, MCPs, KBs), persona body. Templates are **deployed** into projects.

**Agent time** — in what a task took (ruling 83), the sum of `finished_at - started_at` over the task's agent runs that started and ended, in minutes (`runs.agentMinutes`). A run cut by a restart is left out, because boot recovery stamps its end with the boot instant, and so is a run still going; both are counted beside the figure and said on the card, and the stretch one may have been running counts as no wait on a person either. Within a span of wall time (to the first delivery, to acceptance) it is instead the time some ended run covered, so two agents running at once count once. Derived when read in `app/server/tasks/what-it-took.server.ts`, never stored; [task-lifecycle.md §9](../domain/task-lifecycle.md) defines every number of the figure.

**Always-human capabilities** — `merge-pull-request`, `transition-to-done`, `change-project-policy`. A server invariant (`ALWAYS_HUMAN_CAPABILITY_IDS`); no stored grant can hand them to an agent.

**Asked round** — in what a task took (ruling 83), one decision put to a person on a task: each decision a person recorded (a timeline entry of theirs that opens with `**Decision:**`), plus the one open now. One packet is one round, whoever raised it (the operator, an agent's own question, a server escalation) and however many options it carried. A declined recommendation is not a round (nobody was asked a question), nor is a packet withdrawn unanswered, nor a decision answered by accepting, which is the acceptance: an open decision that offers acceptance is counted only once it is answered another way, so answering never lowers the count. A person's comment that opens with the same words is not a decision.

**Attachments** — files under `projects/<slug>/tasks/<KEY>/attachments/`: written by a run granted `attach-evidence-references` (or the browser MCP), or by a person holding `attach-file` through the task page's "Attach a file" or the New task dialog's Files field, which files a task with its input before triage (ruling 76: at most 10 MB a file, of any kind, stored under its name in composed Unicode form and found by either form, audited `task.attachment.added`; a comment or a controller message carries files the same way). A project admin removes one from its card (ruling 80, audited `task.attachment.removed`). Served member-only at `/projects/:slug/tasks/:key/attachments/:file`. Every kind opens an in-app card with a Download button: images the picture; the known binary kinds a "no in-app preview" note; every other file a read-only code reader (highlighted by the name's grammar, numbered), unless a NUL byte in its head shows it is not text; a markdown file opens rendered, its raw text one switch away (ruling 317). At run completion the browser MCP's machine-stamped working artifacts are pruned unless the run cited the exact filename (ruling 78). Files a delivering RUN saved are delivered work a required reviewer must judge; a person's upload is an input and holds nothing (ruling 81). Each files delivery is also kept as it was delivered, under `tasks/<KEY>/deliveries/<stamp>/`, so a rework that saves the same names leaves the delivery a verdict scored readable; `read_board` and the controller's `get_task` list a task's kept `deliveries`, and every `read_task_attachment` opens one with `delivery` (ruling 86). A source a task keeps is not an attachment: see **Sources**.

**Autonomy** — the operator deployment's `supervised | full` setting. Supervised operators recommend at governed boundaries; full operators act. A per-run level is clamped to the configured ceiling (ruling 108).

**Backend** — `claude` (Claude Agent SDK) or `codex` (Codex SDK). A backend is not "configured" or "unavailable" for the instance: it is connected, or not, **per person** (ruling 137), and a run's answer is the health of its own credential principal (`userBackendHealth`: `available` plus a `verification` of `credential | file | presence | none`). The only instance-level number is `connectedUsers`, a count on `/resources/health`. Every Codex run gets a private `CODEX_HOME` forked from the person's home (ruling 145) and runs `danger-full-access`: Viberr does not use the Codex CLI's OS sandbox, so Viberr's own boundaries are the boundary (ruling 144). Display label for `claude` is "Claude" (ruling 298).

**Base refresh** — merging the project's base branch into a task branch (`update_branch_from_base`, a `--no-ff` merge), by the operator, at acceptance, or by a person's `refresh-and-review`. Each is recorded in `task.md` `baseRefreshes[]` `{mergeSha, baseSha, base, commits, at, onto}`. A head reached only through Viberr's own refreshes of the delivered revision is the same deliverable on a newer base, so the revision and its verdicts survive and a re-review of the refreshed head follows (`refreshChainFrom`, ruling 239). **Revision drift** reports base-refresh commits apart from authored ones. The refresh honours file leases (ruling 241).

**Blocked by** — a task's `blockedBy` list (ruling 55): the task keys in the same project it waits on. While non-empty the derived readiness is floored at `blocked`, the task page says what it waits on and in what state (resolved at read time; a board card says only `blocked`, ruling 306(a) and (e)), the task is never "gone quiet", and Viberr releases it itself when every entry is done. The hold refuses every agent dispatch and delivery (ruling 56); a decision the hold refuses is queued rather than consumed (ruling 66). No project may take `EPIC` as its task prefix: `EPIC-1` reads as the epic `epic-1` wherever it is named (ruling 55).

**Board file** — a board's workflow without its work, as one zip in which every part is a plain file (ruling 32): `board.md` (a project.md without its repository, members, counter and leases, plus the knowledge bases, skills and MCP servers it carries), a README, and folders for the agent templates, skills and knowledge-base documents its agents use. Never a task, an epic or a credential. Written by Instance settings → Import & export → Export (`<slug>.viberr-board.zip`), read by Import, which makes a new project from it and brings in what the instance lacks without overwriting anything it has (a resource held differently comes in as a copy, or yields to the instance's, the admin's choice). Format in [file-formats.md §9](../architecture/file-formats.md#9-a-board-file-ruling-32).

**Boundary** — the rule on a workflow edge (`BOUNDARY_VALUES`): `auto` (the operator may cross it), `approval` (a human approves the operator's request), `human` (a human decides). The edge into the terminal stage is always `human` and `locked`.

**Capability** — an id in `UNIFIED_CAP_CATALOG` (`app/shared/capabilities.ts`) with a per-deployment mode (`CAPABILITY_MODES`: `direct | recommend | human | off`). Enforcement scope is `both`, `claude-only` or `advisory` per capability (`capabilityEnforcement`). Specialists never hold `recommend`; a stray one normalizes to `off` (ruling 182).

**Compaction** — two different things. *Timeline compaction* is the anti-noise fold of routine events once a task passes its `compression-threshold` guardrail (`timeline-compaction.server.ts`); typed events are kept, and a comment somebody was notified about is never folded (ruling 20). *Session compaction* is the provider summarizing an agent session's context: Viberr compacts a session whose last prompt is above `COMPACT_AT_COMPLETION_TOKENS` (100k) at the end of a finished or errored run, while its cache is warm, and sets no mid-run window; never after an interrupt or after a run its provider refused, and a compaction's failure is never the run's (ruling 174). A specialist's run has ended by then, so its report waits for nothing and only a run that resumes that session waits for the summary; an operator's session, which nothing resumes, is not compacted (ruling 175). Each session compaction is recorded once: in the run's `compactions` count and as one `task.agent.compaction` audit row, with no timeline note; a size Viberr could not measure is not printed as zero (ruling 172).

**Completion packet** — what the operator hands over at the acceptance boundary, and the task's **result** once it is accepted (ruling 103): `completionPacket` in `task.md`, its summary of the work, what to weigh (`considerations`), what was assumed (`assumptions`) and what is missing (`gaps`), the result's files on a task delivered as files (`files`, named from the delivery, a line each), its summary of the code changes when they run past 200 changed lines (`COMPLETION_SMALL_CHANGE_LINES`), and the screenshots it picked from the task's image attachments, a caption each. Written with `write_completion_packet` and bound to the **review subject** like a **verdict**, so a new delivery makes it stale. Every operator offer to accept waits for one that describes the current subject; a person's acceptance does not. The task page shows it inside the decision that offers acceptance, with each reviewer's verdict and the change read live beside it: the diff whole at 200 lines or fewer, else the summary with the diff one press away. On an accepted task the same card is titled "Result" and stays: a task delivered as files shows its result files, and one delivered as a revision shows its pull request, the change's size and the paths it changed.

**Connection** — an org-level GitHub owner + PAT (`github_connections`). Distinct from a user's stored PAT (`github_pats`) and from a project's credential binding (`project_github_credentials`).

**Controller** — the single instance-level conversational agent (`kind: controller`) reachable at `/controller`, `/projects/:slug/controller` and, on every signed-in surface, through the controller dock. Every tool call runs under the asking user's live authority (ruling 247). Its configuration is deployment-locked by default (ruling 270); it may record a request for a grant it cannot make itself (`request_resource_grant`, ruling 271).

**Controller dock** — the floating Controller button (bottom-right, every signed-in surface except the controller pages, login, profile and notifications) and its non-modal panel, bound to the place the person is standing (ruling 256). A **conversation scope** is that binding: instance, one board, or one task; the server gathers the scope as a **context read** at the start of every turn (the task's `task.md` verbatim and bounded, or a board snapshot, or the person's projects). A user message's **surface** is the page it was sent from. A reply its owner has not yet seen (`controller_conversations.seen_seq`) marks the button with a still dot and the thread in every list (**unseen reply**, ruling 257).

**Credential principal** — the ONE person an agent run bills, persisted as `agent_runs.credential_user_id` (ruling 137). Task runs (operator, specialist, resume, scheduled, boot recovery, retry) use the **task owner**; controller turns use the **asker**. Resolved by `run-principal.server.ts`, which either returns the principal and their backend health or a typed refusal (`unowned`, `owner-missing`, `no-credential`) whose single human sentence comes from `principalRefusalMessage`. A refused run writes an honest `run·unavailable` error run and starts no process; the column is NULL only on such a run.

**Data root** — `VIBERR_DATA_ROOT`. Holds canonical files, SQLite, run logs, KBs, skills and the per-person agent homes under `runtimes/users/` (ruling 137). One app process per data root, enforced by `state/writer.lock`.

**Decided packet** — an `edit_goal` packet whose option was confirmed: `awaiting: goal_edit` plus `decided { optionIndex, at, byUserId }`. It reads as decided on every surface (display readiness `goal_edit_pending`), and its only way out is saving the edited goal, prefilled by `goalDraftForOption` from the option's `goalDraft` (ruling 63).

**Decision packet** — the one open structured question on a task (`## Packet` in `task.md`): `type` `input | blocked`, `from` (the operator, or `policy-engine` for a packet Viberr raised itself, such as a review deadlock), observations, and options whose `kind` is one of the 21 `PACKET_OPTION_KINDS` (`accept_completion`, `request_edit`, `block_on_policy`, `hold_runtime_debug`, `redirect`, `retry_other_backend`, `edit_goal`, `archive_task`, `discard_branch`, `resolve_remote_collision`, `force_accept`, `move_stage`, `wait_for_window`, `accept_unverified_head`, `block_on_dependencies`, `question_reviewer`, `create_task`, `deliver_for_review`, `connect_repository`, `keep_without_repository`, `custom`). Resolution dispatches on the kind, never the title (ruling 62(a)), which is why an option's title is a promise its kind has to keep: a send-back option whose words describe a force-accept, a stage move or an agent-profile edit is refused where it is authored, and named for the kind that performs it; an option whose premise is false is refused where it is written (ruling 131). `create_task` makes a new task under the resolving person's own authority (ruling 67), and `deliver_for_review` delivers a committed head nothing has delivered, through the task page's own delivery (ruling 62). `connect_repository` and `keep_without_repository` are the two answers to the **Repository question**, written only by `ask_for_repository` (ruling 107). A failed run's recovery packet names the cause Viberr classified and the credential principal's own remedy, and a recovery option's label states what the human asserts; its recorded decision is that label or its pre-authored `ev` (ruling 156).

**Delivery** — pushing the task branch and opening the review PR. An operator decision (capability `deliver-review-pr`, ruling 126) executed by the server; specialists never push and nobody pushes by hand. Humans can trigger it directly (`deliver-review` intent). Delivery is defined by the remote (ruling 229): the push reads origin's head first, answers `up_to_date` when it already carries the workspace head, and otherwise pushes and says what moved; rework on a task whose PR is already open is delivered the same way and moves that PR's head. A push that changes a path another active task holds by **file lease** is refused before anything reaches GitHub. A deliverable that is not a commit (files a run saved) is delivered work too, reviewable like one (rulings 81, 84), and has no branch or pull request to deliver: `performDelivery` refuses one and the task page offers none (ruling 102).

**Deployment** — a `project.md` `agents[]` entry `{profileId, capabilities, extras, definition?}` that puts a template on a project with a project-effective capability policy.

**Diagnostics** — tolerant-parse findings (`info | warning | error`, `hardStop`). Warnings floor readiness at `input_required`, errors at `inconsistency_risk_detected`, hard stops at `blocked`; a hard-stop file is read-only to the app (`file_not_trusted`).

**Dispatch** — running a deployed agent on a task (`run_agent` for the operator, the `run-agent` intent or the controller's `run_agent_on_task` for humans). A human's dispatch prompt is recorded as their own `@<agent>` comment BEFORE the run starts, so the run is the only delivery of it (ruling 69). Refused because that agent is already running, the prompt is delivered when its current run finishes, and the note and the reply say so (ruling 152). Running an unengaged profile **engages** it; delivering iff the task has no deliverer and the profile holds repo-write, supporting otherwise (ruling 51). Refused outright on an **archived** task, like every other governed mutation on one, and on a task a dependency hold holds (ruling 56). The STAGE is a separate question: ruling 181 licenses engaging an eligible profile at any stage, terminal included.

**Engagement** — an entry in `task.md` `engagements[]`: `{profileId, backend, role, delivers, verdictCapable, pinnedBackend?}`. At most one has `delivers: true` (the **delivering engagement**, owner of workspace, branch and PR). Others are **supporting engagements**; a supporting engagement with `verdictCapable: true` is a **required reviewer**. A project may also declare **required reviewers per review stage** in `project.md` (`requiredReviewers: [{stageId, profileId}]`, ruling 89): such a reviewer is required on every task that delivered work, in any form, whether or not it was engaged (ruling 81), and a task is not acceptable until it holds an approve verdict on the current review subject. Stage eligibility gates NEW engagements only (ruling 181): once a profile is the task's delivering engagement it may be prompted or resumed on that task at every stage, while a supporting engagement runs only at the stages its profile declares.

**Epic** — a named body of work in one project, the way Jira draws an epic and Linear a project (ruling 272), canonical at `projects/<slug>/epics/epic-<n>.md` (`EPIC_STATUS_VALUES`: `planned | in_progress | paused | done | cancelled`, a person's call, never derived; a colour from the stage presets; a lead, start and target dates). Tasks join and leave it one at a time: the membership is the task's own `epic` field, so a task is in at most one epic, and the epic's **progress** (done of total, started, not started, held; archived tasks apart) is counted from its tasks when it is read. It starts, orders and holds nothing: what a task waits on is its own **Blocked by**. `manage-epics` creates and edits one; moving a task in or out is `edit-task-meta`; the operator moves its own task with `set_epic`. Nothing deletes an epic: a done or cancelled one stays readable. Seen on the Epics pages, the task page's hero and Details, the board's epic filter, and the controller's `list_epics`, `get_epic`, `create_epic` and `update_epic`.

**File lease** — a `project.md` `fileLeases: [{paths, taskKey, reason}]` row (ruling 60): path globs (`*` within a segment, `**` across segments) that one task owns until it merges. A delivery, and a base refresh (ruling 241), that would change a path leased to another active task is refused, the refusal quoting the reason. A lease whose holder is archived, terminal or gone is spent and binds nobody (ruling 60). Leases are edited on Settings → File leases or by the controller's `set_file_leases`; the operator may lease paths to its own task with `lease_files`, first come first served, never overlapping another active lease, and not when that would park work other tasks wait on (ruling 61).

**Goal (chained goal)** — gone (ruling 273): a chain of **links** the server advanced, one task per link, as the work each link waited on landed. Boot converts every chain it finds into the **Epic** with its number, its tasks in it and its unstarted links made held tasks or listed in the epic's description; the files are kept under `projects/<slug>/goals/converted/`. Not to be confused with a task's own goal (`## Goal`, its acceptance contract), which stays.

**Guardrails** — per-project anti-noise rows in `project.md`: `meaningful-comment`, `no-duplicate-summary`, `compression-threshold` (default 40 events), `evidence-separation`; plus the `delete-branch-after-merge` row the branch-cleanup policy reads. There is no `operator-brevity` row (ruling 134). Edited on Policy → Guardrails (toggle, threshold value, removal of retired rows; ruling 134); the branch-cleanup row is edited on Settings.

**Guest** — a registered user who is not a member of the surrounding project. Renders as a pill on their comments.

**Knowledge base (KB)** — a folder under `kb/<dir>/` whose text documents a granted run receives as an INDEX of document names and headings, reading the bodies it wants with `read_knowledge_doc` (ruling 205). The folder may also hold files that are not documents: a report template, a sample, a logo, uploaded by a person or copied from a task by the controller (`copy_task_file_to_knowledge_base`, ruling 205). The index names them under the documents, and a run with a shell opens one in the folder. Grants reference the **directory**, never the display name. Repo-documented conventions outrank KB guidance (ruling 206). See also **Rulings knowledge base**.

**Knowledge-base correction** — a passage of a knowledge-base document that an agent on a task proved wrong, rewritten or deleted in place by that agent with its evidence, or text it added (ruling 210; the edit rules in [file-formats.md §8](../architecture/file-formats.md)). Any knowledge base a run on the task was given, the project's rulings included: a specialist writes it with `correct_knowledge_doc` (a Codex one through the gateway's `viberr_knowledge` server, ruling 216), the operator with its own, which also relays a Codex agent's reported correction when the gateway is not running. Nobody approves it first. Its id is `kc-` plus ten hex characters, and its record is the `task.kb_correction.merged` audit row, which keeps the replaced passage. It reaches the task's timeline as a short `kb_correction` event, with its evidence (ruling 211; `read_timeline_entry` reads all of it whole), `get_project` as `kbCorrections`, and the project Controller page's Knowledge base panel, where an org admin's Undo puts the passage back (`task.kb_correction.undone`; `undo_kb_correction` for the controller). An agent that tries to write back a correction a person undid is refused.

**Knowledge-base proposal** — a correction filed, not binding, under "## Proposed corrections (not binding)" in the document it corrects, with the line it corrects and the evidence, for a person to promote (ruling 267; format in [file-formats.md §7](../architecture/file-formats.md)). Nothing files one now (ruling 210(c)); documents keep the ones they hold, the controller's turn context and `get_project` (`openProposals`) list them, and the Controller page's Knowledge base panel offers an org admin Promote, Dismiss and Promote all, which ask the controller to close them with `resolve_kb_proposal`. Its id is `kp-` plus ten hex characters. Audited `task.kb_proposal.filed`, `org.kb.proposal_promoted`, `org.kb.proposal_dismissed`.

**MCP server** — an org-registered Model Context Protocol server (`HTTP` or `stdio`) a profile may be granted. Granting a server is the whole authorization for its tools, except its **write tools** (ruling 188). Names in `RESERVED_MCP_NAMES` (`viberr`, `viberr_agent`, `viberr_browser`, `viberr_controller`, `viberr_ops` and their hyphen forms) belong to Viberr's in-process servers.

**Operator** — the one agent that drives every task (`kind: operator`, one deployment per project), always called Operator and with no role (ruling 106). It triages, dispatches agents, opens packets, recommends or performs transitions, leases files to its task, corrects the project's rulings in place (ruling 210), and decides delivery. It never writes code.

**Org role** — `users.role`: `admin | member`. Governs instance surfaces (org settings, insights, audit export). Distinct from project roles.

**Owner** — the one human on a task (`ownerUserId`), seated at creation as the creator or as the member named at creation, before the first operator run (ruling 48). Contributor or above may take or release; the owner governs any open decision on their own task, including accepting completion (FR37, ruling 50), and every agent run on the task bills the owner's own agent accounts, so an unowned task cannot run agents at all.

**Page capture** — Viberr's own picture of a delivered page (ruling 86). When a files delivery is stamped, each `.html`, `.htm`, `.md` or `.markdown` file an agent delivered is rendered in a headless browser at a desktop width (1280 px) and a phone width (390 px), as the task owner's agent user and with no network, and kept as `<file>.capture-desktop.png` and `<file>.capture-phone.png`: in the task's attachments, in the kept delivery it pictures, in `task.md` `pageCaptures` (bound to that delivery's `deliveredAt`), and under one timeline note from "Page capture" (audit `task.pages.captured`). The completion and Result card show the pictures beside each result file that is a page. Stored HTML is still never rendered on the app origin (ruling 317): the picture is an inert PNG. An HTML page is measured as it is pictured (ruling 328): what the accessibility checks find at each width, which controls the keyboard does not reach, what still moves with reduced motion asked for, its weight and its load time on a slow phone line, kept in the record (`measured`), said in the note and set beside the lightest and fastest page the board has had accepted. An agent that holds the board readers asks for the same picture of any page on its task with `capture_page`, which keeps nothing and also shows the page in a state (a control pressed, under the pointer or holding focus, with reduced motion asked for, or at three moments while it moves), and for the same figures with `measure_page`. A reviewer's approval of a delivered HTML page is recorded only from a run that was shown the whole page at both widths (ruling 329). Never a file a run is credited with, a result file or a screenshot the operator picks; Viberr's own picture is the one of a page the task holds or one the record names (`pageCapturesAmong`), so an agent's own file that only ends `.capture-desktop.png` stays that agent's. A delivery that is a revision is not pictured.

**PR state** — the `task.md` `pr.state` cache (`PR_STATE_VALUES`): `review` (open or draft), `merged`, `closed` (closed unmerged), `accepted` (a full-autonomy operator accepted; merge pending for a human). Beside it the reconciler keeps `pr.review` (`approved | changes_requested | review_required`), `pr.mergeable` (`clean | conflicting | unknown`, pinned to the head it was measured on, ruling 242) and `pr.paths` (the changed paths, ruling 242). Sync pill precedence: merged > behind > synced.

**Project role** — `admin | maintainer | contributor | viewer` (`PROJECT_ROLES`), a strict tier stored in `project.md` `members[]` and enforced through `app/shared/rbac.ts`. Membership is the outer gate: non-members get a 404 (ruling 27).

**Projection** — a SQLite row derived from a canonical file. **Rescan** reconciles changed files by content hash; **rebuild** drops all derived rows and re-projects everything.

**Prompt cache** — the provider's cache of a session's prompt prefix. Every run stores what it did (ruling 172): whether the first call was a warm or cold start, the tokens written to and read from the cache, the TTL bucket (`cache_ttl_bucket`: `5m | 1h | mixed`, Claude only), the peak and last prompt size and the compaction count. The Agent-logs console and the Insights **Prompt cache** table show it; a figure a backend never reports is not a zero (Codex reports no cache writes, ruling 36). The TTL is the CLI's own choice, and a cache or compaction switch in the server's environment never reaches a run (ruling 171). A session idle past its cache lifetime whose last prompt exceeds 150k (`RESUME_FRESH_CONTEXT_TOKENS`) is not replayed; the run starts fresh through the continuity reset (ruling 173). Insights sorts resumes by idle time against the lifetime each backend and credential kind is assumed to have, and counts operator bursts (ruling 172): the measurements the plan asked for before the Codex lifetime moves or a start gate is built.

**Provenance** — the `provenance` table: what the projector and reconciler observed, and when. Not retained; not user-facing except freshness chips.

**Readiness** — the stored 4-value enum `ready | input_required | inconsistency_risk_detected | blocked` (`READINESS_VALUES`, ruling 44), derived only in `readiness-policy.server.ts`; a non-empty `blockedBy` floors the derived value at `blocked` (ruling 55). Surfaces additionally render the derived display values `agent_working` while `waiting === "agent"`, `agent_queued` when the run carrying the task is parked behind the concurrent-run cap (ruling 44), `goal_edit_pending` for a decided packet, and "accepted" / "merged" for done-stage tasks (`READINESS_DISPLAY`).

**Recommendation** — a pending card the supervised operator leaves on a task (`RECOMMENDATION_KINDS`): `transition`, `run_agent`, `accept_completion`, `delivery`. Apply executes the same mutation a human would; Dismiss records it. An `accept_completion` card binds to the work revision it was made for (`forHeadSha`) and is withdrawn, on the record, when that revision is replaced, a packet opens, or the task leaves the acceptance boundary (ruling 99).

**Repository bootstrap** — ruling 227: when the project's default branch has no ref (an empty repository, or one whose only refs are task branches), Viberr creates it before a task's first branch, by an initial commit or at the first commit of GitHub's current default, disclosed on the timeline and audited as `github.repo.bootstrapped`. Where the repository has a default branch of its own that is not named for a task, nothing is created: a project naming a branch the repository does not have takes that one (ruling 227, `project.default_branch.adopted`).

**Review deadlock** — a required reviewer that returns `request_changes` on consecutive rounds. Round two is the operator's: it puts the completeness question to the reviewer itself (ruling 93). At `REVIEW_DEADLOCK_ROUNDS` (3) consecutive objections from one reviewer, Viberr opens a `policy-engine` packet for a person (ruling 94, `task.review.deadlock`). A rework the provider refused fought no round (ruling 92).

**Revision (work revision)** — the identity of the work under review: `{id, headSha, treeSha, branch, createdAt, sourceProfileId, kind}`, `kind` one of `delivered | verified | discarded | external` (absent reads as `delivered`; `discarded` is a retired record after `discard_branch`, ruling 234; `external` is minted from a PR head moved by commits Viberr did not deliver, ruling 240). A new head with a different tree mints a new revision, which stales every prior verdict, except a head reached through Viberr's own base refreshes (ruling 239). A verdict binds to the **review subject**: the revision id, or `files:<deliveredAt>` when the deliverable is not a commit (ruling 84).

**Repository question** — the operator's one question on a board with no repository, asked when a task needs one (`ask_for_repository`, ruling 224). Its packet has two answers, both a project admin's: `connect_repository` attaches the repository the person types and starts the controller on the board to switch it to pull requests; `keep_without_repository` writes `no-repository-<project>.md` into the project's **Rulings knowledge base**, and while that document stands the question is not asked again. Every such packet on a board carries `cause: repository:<slug>`, so one answer reaches each task that asked.

**Revision drift** — how far the PR head has moved past the reviewed revision, recorded by the reconciler as `pr.revisionDrift {headSha, authored, baseRefresh}` (ruling 239). `authored` counts commits since the review that are the branch's own and not a merge Viberr recorded in `baseRefreshes`; `baseRefresh` counts the base commits and clean merges an `update_branch_from_base` brought in. `describeRevisionDrift` prints the one sentence every surface shows; only authored commits are "unreviewed". A base refresh is reported as a base refresh.

**Ruling** — a numbered owner decision recorded in [decisions.md](../architecture/decisions.md). Code comments cite them as "ruling N". Each states its decision as it holds today; a changed decision is rewritten in place, and a citation must name a ruling the file defines (ruling 1).

**Rulings knowledge base** — the ONE knowledge base a project names as its settled rulings (`project.md` `rulingsKb`, set through the controller; ruling 208(a)). Every run on the project reads it, whatever its profile's grants. The operator may correct it in place with `correct_knowledge_doc`, including the conventions review shows are missing (ruling 210(a)). See **Knowledge-base proposal**. Audited `project.rulings_kb.updated`.

**Run** — one execution of an agent through a backend: `agent_runs` row + raw NDJSON transcript. `kind` is a delivery axis (`operator | primary | reviewer | controller`; `primary` and `reviewer` are **slot-model names**); `state` is `queued | running | finished | error | interrupted`. An `interrupted` run names who stopped it (`interrupted_by`, a person) or why (`interrupted_reason: restart`, boot recovery); a restart is never an error. `credential_kind` records how the principal's account was connected (`login | api_key | access_token`).

**Run failure kind** — why an errored run ended, the `RunFailureKind` enum in `app/shared/run-failure.ts`: `quota | auth | unavailable | overloaded | max_turns | max_budget | idle_timeout | tool_loop | session_missing | unknown`. Read from the terminal line's typed `failure` record first (ruling 155(a)), then the `run·error·<kind>` tag suffix, then prose. `quota` and `auth` are the account's (remedy on Profile → Agent accounts), `unavailable` means no credential (no process started), `overloaded` the provider's side (retry), `max_turns` and `max_budget` are cut-offs by the turn cap and the spending cap (not task failures), `idle_timeout` a hang, `tool_loop` a run the MCP gateway stopped for sending one call and getting one answer again and again (ruling 158(b)), `session_missing` a resume whose transcript is gone.

**Schedule** — a future run recorded in `task.md` `schedules[]`: `run-operator` (optional steer) or `run-agent` (a profile id + prompt). Statuses `pending | claimed | fired | failed | cancelled`. Resolves the live deployment at fire time; never fires on a terminal task. A task whose only way forward is a pending schedule reads `waiting: schedule` (ruling 45). Made from the task page, by the controller (ruling 264), or by the operator for its own task (`schedule_task_action`, ruling 125: a wait a clock explains is scheduled, never asked, and a hold a pending schedule explains needs no packet).

**Scope violation** — a recorded PAT permission gap (`scope_violations`), opened by the reconciler or a refused push, resolved by re-validating the credential. The rail's Settings badge counts open violations; an advisory scope (one merging never needed) is a note, not a violation (rulings 221, 221(b)).

**Sent back** — in what a task took (ruling 83), the times the work was returned: by reviewers, each request for changes that bound to a delivery and fought a round (the `quality` notes titled "Changes requested" and nothing more, so an approval that later replaces the verdict does not erase it, and two reviewers objecting to one delivery count two; an objection that bound to nothing is titled "Changes requested, not counted", a repeat on work nobody reworked "Changes requested, on unchanged work", and neither is counted); by people, each move of the task to an earlier stage a person made. A decision a person answers with a request for changes is an asked round instead, and an `@agent` comment that restarts work is counted in neither.

**Session export** — `/resources/session-export?run=<id>`: a bash installer carrying the provider transcript so a run can be resumed locally with `claude --resume` / `codex resume`.

**Skill** — a folder `skills/<name>/SKILL.md` (plus supporting files). Claude runs load granted skills through the SDK's native skills mechanism; Codex runs get the body injected as prompt text (ruling 185). Every writer refuses a SKILL.md body that is not a skill (ruling 186).

**Slot-model names** — names kept from the static delivering and reviewer slots that ruling 180 replaced with dynamic dispatch; they mean engagements now, not slots (ruling 21). In the task projection, `specialist_json` holds the **delivering engagement** (`deliveringEngagement`, null while the task has none) and `reviewers_json` the **supporting engagements** (`supportingEngagements`, in `engagements[]` order), whatever their roles; a supporting run's thread id `r<n>` is its index into that list. On a run, `kind: primary` is the delivering engagement's run and `kind: reviewer` any supporting engagement's run: a Developer dispatched with `delivers: false` runs as `reviewer`, so the kind alone does not make a run a **required reviewer**'s. Read `role` and `agent_profile_id` for who ran. The names stay because `agent_runs` rows are app-owned, so no rescan can rewrite them, and the two single-flight indexes key on `kind`.

**Sources** — what a task's result rests on, kept apart from its files (ruling 82): a page as an agent fetched it, a repository file at a commit, an API answer, a command's output. An agent that may save files on the task (`attach-evidence-references`) saves the bytes in the attachments folder under a name that starts with `.source-`, which nothing lists, posts or delivers, and calls `keep_source` with that name, where it came from and a title; the server takes its own copy into `projects/<slug>/tasks/<KEY>/sources/` under an id (`S1`, `S2` and so on) with the time, the agent, the run, its size and its SHA-256, and removes the staged file. An agent whose "Search & fetch from the web" is withheld keeps what it can reach (a repository file, a command's output) and is told it keeps no page. It differs from an **attachment** in four ways: it is never a file of the result (no reply posts it, no delivery carries it, the working-file prune never sees it); it is never overwritten or removed (the folder is the server's own, which an agent reads and cannot write, and nothing prunes it); it carries where it came from, as the agent stated it, and which run kept it; and nobody attaches one by hand. Every reader of the task (a reviewer, the operator, the controller) lists and opens them with `read_task_source`, and searches one with its `find`, which answers the places that hold a word or phrase, each with its line (ruling 82); a member on the task page's Sources panel and the Result card, served member-only at `/projects/:slug/tasks/:key/sources/:id` under the same headers as an attachment, so a kept HTML page never renders on the app's origin. Each files delivery records which sources the task held when it was delivered, a revision rests on the ones kept by the time it was minted, and a claim with no kept source behind it reads as unsupported. Limits: 10 MB a source, 200 sources and 100 MB a task. Audited `task.source.kept`. A source can be part of a **look** (ruling 327): how a page on the web looked when `keep_page_look` pictured it, kept as the whole page in stretches at 1280 px and 390 px, its first screen at three moments while it moved, and a note of what moved, all under one address and one date. Work made to look like that page is made to those pictures and judged against them, never against the address as it reads later or a description of it, and a reviewer's approval owes a look at each (ruling 329); another task of the project takes the same look over. Audited `task.page_look.kept`. Format: [file-formats.md §10](../architecture/file-formats.md).

**Spending cap** — `maxRunSpendUsd`, the instance's cap on what one Claude run may spend, in USD (ruling 159; Instance settings, org admins only, none by default). Every run carries it as `RunSpec.maxSpendUsd`; the Claude SDK stops a run past it (`error_max_budget_usd` → failure kind `max_budget`). Codex has no budget option, so it does not bind Codex runs.

**Stage colour** — one of the twenty named presets in `STAGE_COLORS` (`app/shared/workflow/stage-colors.ts`: slate, gray, stone, red, orange, amber, yellow, lime, green, emerald, teal, cyan, sky, blue, indigo, violet, purple, fuchsia, pink, rose). The name is the stored value and the stylesheet the paint (`data-stage-color`, `--stage-*` tokens); an added stage takes the first default no sibling wears (`nextStageColor`), a missing value reads `slate`, and `recolor-stage` refuses a name outside the list (ruling 279).

**Stage roles** — `entry` (the first stage), `terminal` (the last), `review` (the stage with an edge into terminal) and `work` (the stage with an edge into review), derived from the per-project stage list and workflow graph (`resolveStageRoles`). Stage ids are never hard-coded.

**Timeline event** — a `### <ISO> · <type> · <actor>` block in `task.md`, `type` one of the 13 `TIMELINE_EVENT_TYPES` (`comment`, `completion`, `github`, `policy`, `note`, `quality`, `transition`, `blocked`, `agent`, `assign`, `continuity`, `proposal`, `kb_correction`). `policy` is reserved for genuine violations and refusals; neutral system remarks are `note`; a proposed knowledge-base correction is `proposal`, labelled "Proposal" (ruling 267); a correction an agent wrote, or a person's undo of one, is `kb_correction`, labelled "Knowledge base" (ruling 210).

**Validation** — the derived review-state cache in `task.md`: `healthy | changed | failing | none | bypassed` (`VALIDATION_VALUES`, `deriveValidation`; `bypassed` only for a force-accepted task). Never hand-edit it.

**Verdict** — a required reviewer's `approve | request_changes` (`REVIEW_VERDICT_RESULTS`), bound to the review subject (a revision id, or `files:<deliveredAt>`). A project member's GitHub approval on the PR, bound to the delivered head, counts as an approving verdict (ruling 245).

**Waiting** — whose turn it is (`WAITING_VALUES`): `human | agent | none | schedule`. Forced to `none` in the terminal stage; `none` while a task waits on other work with no packet or recommendation open (ruling 55), and `human` again once the wait is released. `schedule` is derived by the projection, never written to a file: the file says `human`, but nothing a person could do is open and a pending schedule will pick the task back up (ruling 45).

**Workspace** — the delivering engagement's git clone under `tasks/<KEY>/workspace/<repo>`; supporting runs get `workspace/support/<profileId>/<repo>`. Cut from a per-project mirror; reclaimed once the task is terminal. On a project with no repository (ruling 199) it is the bare `workspace/` folder, scratch space with nothing in it delivered.

**Write tool** — a tool on an org MCP server that an org admin marked in the server's editor (ruling 188). A run that withholds `execute-code-or-write-repo`, and every operator run, does not get it: Claude denies it by name, Codex lists it in the server's `disabled_tools`. The editor suggests names holding create, delete, merge, push, update, write or remove, and stores only what the admin saves; every server row says where it stands (ruling 188), and Viberr makes no claim about the tools left unmarked.
