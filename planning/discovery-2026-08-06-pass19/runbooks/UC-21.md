# UC-21 — Blocker → operator opens a BLOCKED decision packet; human resolves it via the UI

## Purpose

Proves the blocked-packet half of **FR26/FR35** and the full resolution loop:

1. `operatorOpenPacket` with `packetType: "blocked"`
   (`app/server/tasks/operator-actions.server.ts:686-854`): sets
   `readiness: blocked` + `waiting: human`, writes a typed **`blocked`** timeline event
   ("**Blocked:** <title>. Opened a decision packet for the owner to resolve."), audits
   `task.operator.packet_opened {type: blocked}`, notifies watchers
   ("Blocked — decision needed: …"). Deliberate non-behavior (F7-VAL1): `validation` is
   NOT touched — blocked-ness lives on readiness alone.
2. `resolvePacket` (`app/server/tasks/task-actions.server.ts:4107-4560`), the
   `redirect`/`custom`/`request_edit` default branch (:4425-4444): packet cleared,
   `readiness → ready`, `waiting → agent`, the human's free-text note carried onto the
   decision event as a `> ` blockquote (P11-71), audit `task.packet.resolved`, and the
   promise "the operator re-engages" is kept — the operator is re-invoked fire-and-forget
   (:4508-4560).
3. **B3** single-decision invariant: while the packet stands, another packet is a refused
   `noop`, never a replacement (`operator-actions.server.ts:731-738`).

## Steps

1. **Create the task** (Variant A goal) via
   `POST /projects/viberr-core/board` `intent=create-task title=... goal=...`. Record
   `<KEY>`. The create-trigger operator run starts within ~5 s. [API]
2. **Wait for the operator turn to finish** (poll `agent_runs`; 1–3 min). If no packet
   resulted, execute Variant B and wait for the queued human turn. [API]
3. **Assert the blocked packet.** [API] `task.md`:
   - `## Packet`: `type: blocked`, `kind: Blocked decision`, `from: operator`, 2–4
     options (valid kinds; expect `custom`/`redirect`-shaped choices, possibly
     `archive_task`), exactly one `rec: true`.
   - Frontmatter: `readiness: blocked`, `waiting: human`.
   - `validation` UNCHANGED (`none` for a fresh task) — blocked must NOT fake a failing
     review (F7-VAL1).
   - Timeline: a typed **`blocked`** event ("**Blocked:** <title>. Opened a decision
     packet for the owner to resolve.").
4. **[UI] Surfaces:** task page renders the packet at the top (above timeline, FR25) with
   a Blocked-toned readiness pill; board card selected by the **"Blocked or waiting"**
   chip; bell shows "Blocked — decision needed: <title>". State is text+icon+emphasis,
   never color alone.
5. **[API] Audit:** `task.operator.packet_opened {type: "blocked"}` in Activity → Audit
   logs.
6. **B3 probe (optional):** `intent=run-operator` → after that turn, the packet `id` is
   unchanged (a manual turn may comment, but must answer FROM the packet, not replace it).
7. **Resolve via the UI.** [UI] In the packet, select the continue/redirect-shaped option
   (kind `custom` or `redirect`), type the note
   `Proceed with the standard pass<NN>-<topic>.md format; agents may start.` and confirm.
   [API equivalent] `intent=resolve-packet option=<0-based index> note=...`.
   Expected toast: `Decision recorded: <option title>`.
8. **Assert the resolution.** [API] `task.md`:
   - `## Packet` GONE (null); `readiness: ready`; `waiting: agent`.
   - Timeline decision event: `**Decision:** <option title>. …` with the note as a
     `> ` blockquote beneath it (P11-71).
9. **Assert the re-engagement promise.** A NEW operator run row appears for `<KEY>`
   within ~10 s (the resolution's fire-and-forget hand-off) and its turn honors the steer
   (Variant A: it will now coordinate the marker work — engaging the Doc Writer is the
   expected next move). [API poll `agent_runs`; UI Agent logs]
10. **Audit + notification:** `task.packet.resolved`
    `{optionKind, optionTitle, packetKind: "Blocked decision"}` naming Arda; the packet's
    "Waiting on you" bell row is cleared (`markTaskPacketApprovalRead`). [API + UI]

## Expected outcomes (PASS evidence)

- Blocked packet: file + typed `blocked` event + `readiness: blocked` + audit +
  notification, with `validation` untouched. [API/UI, steps 3–5]
- Resolution: packet cleared, `readiness: ready`, `waiting: agent`, note on the decision
  event, audit row, bell cleared. [API/UI, steps 8/10]
- Operator re-invoked after the redirect/custom resolution (step 9) — the task is not
  left `waiting: agent` with nothing running and nothing queued.
- B3 held throughout: at no point did a second packet replace the first.

## Failure signatures (findings)

- Packet opens but `readiness` stays `ready` → **NEW HIGH**: `operatorOpenPacket` blocked
  branch regression (board would not flag a blocked task).
- Packet sets `validation: failing` → **NEW MED**: F7-VAL1 regression (blocked-ness
  leaking into review health; acceptance copy would lie "the latest review is failing").
- Resolution clears the packet but `waiting` stays `human` or `readiness` stays `blocked`
  → **NEW MED** (B-WF2 class: a settled decision must stop waiting on a human).
- The typed note is missing from the decision event → **NEW MED** (P11-71 channel lost;
  the operator would act on an unstated reading).
- No operator run within ~30 s of a `custom`/`redirect` resolution → **NEW HIGH**: the
  "operator re-engages" promise broken (`task-actions.server.ts:4508-4560`) — the task
  strands at `waiting: agent`.
- The re-invoked operator immediately re-opens an equivalent blocked packet, ignoring the
  resolution steer → **NEW**: coordination loop (record both packet bodies verbatim).
- Any second packet REPLACES the open one (id changed without a resolution) → **NEW
  HIGH**: B3 regression.
- Timeline event for the packet is `comment`-typed instead of `blocked` → **NEW LOW**
  (state-semantics: blocked must not collapse into generic chatter).
- Operator (Variant A AND Variant B) consistently refuses to open a packet across ≥2
  attempts → **NEW**: operator-instruction finding against `operatorTurnInstruction` /
  persona (one refusal is nondeterminism; a pattern is a finding).
